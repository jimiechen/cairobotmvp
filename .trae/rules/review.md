# 评审规则

## 1. 评审目标

评审不是只看代码能不能运行，还要确认：

- 是否符合 PRD。
- 是否符合 ADR。
- 是否符合 TDD。
- 是否有范围蔓延。
- 是否有缺失测试。
- 是否影响已有接口。
- 是否需要更新文档。

## 2. 评审维度

每个 PR 至少检查：

1. 需求一致性。
2. 测试覆盖。
3. 代码可读性。
4. 模块边界。
5. 错误处理。
6. 日志和调试信息。
7. 文档同步。
8. 依赖变化。
9. 兼容性影响。

## 3. AI 评审输出格式

Trae 或 AI 评审时必须按以下结构输出：

```text
一、结论
可合并 / 建议修改 / 必须修改

二、符合要求的部分

三、必须修改项

四、建议修改项

五、测试缺口

六、文档缺口

七、风险提示
```

## 4. 不允许合并的情况

不得合并：

- 测试缺失。
- 核心逻辑无测试。
- PRD 未覆盖。
- ADR 冲突。
- 文档未同步。
- 变更范围过大。
- 引入未说明的新依赖。
- 协议变更未更新协议编号注册表。
- Protobuf 的 max + min 编号冲突。
- 未同步更新 OpenAPI 映射。

## 5. 协议变更评审检查项

对于涉及协议变更的 PR 必须检查：

1. [ ] 是否更新了 [协议编号注册表.md](../../docs/api/协议编号注册表.md)
2. [ ] 是否确保了 max + min 编号唯一性
3. [ ] 是否更新了 OpenAPI 映射
4. [ ] 是否更新了 Protobuf 文件
5. [ ] 是否更新了相关测试用例
6. [ ] 是否更新了 LLM Wiki
7. [ ] 是否在 PR 中说明了协议变更的影响
