# TDD 开发规则

## 1. 基本原则

本项目使用 TDD 红-绿-重构流程。

所有核心业务逻辑、状态机、协议解析、AI 过滤逻辑、固件控制逻辑、App 流程逻辑都必须先写测试。

## 2. 红：先写失败测试

实现前必须先写测试。

测试必须描述：

- 输入是什么。
- 期望输出是什么。
- 状态如何变化。
- 异常情况如何处理。
- 不允许发生什么。

测试必须先失败，且失败原因必须符合预期。

## 3. 绿：最小实现

实现时只写让当前测试通过的最小代码。

不得：

- 顺手实现未来功能。
- 引入不必要抽象。
- 修改测试含义。
- 扩大 Issue 范围。

## 4. 重构：保持行为不变

测试通过后可以重构。

重构必须满足：

- 外部行为不变。
- 测试全部通过。
- 命名更清晰。
- 结构更简单。
- 重复更少。
- 不引入无关依赖。

## 5. 测试类型

根据模块选择测试类型：

- AI 模块：单元测试、参数化测试、安全用例测试。
- 固件模块：状态机测试、Mock 硬件测试、协议解析测试。
- App 模块：状态机测试、ViewModel 测试、流程测试。
- 协议模块：序列化、反序列化、兼容性测试。
- 集成模块：端到端流程测试。

## 6. 禁止行为

不得：

- 先写实现再补测试。
- 删除测试来通过构建。
- 只测正常路径，不测异常路径。
- 用 Mock 跳过核心逻辑。
- 让测试依赖真实外部服务。
- 在单元测试中直接调用真实大模型接口。
