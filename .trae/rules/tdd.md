# TDD 开发规则

## 1. 工程级 TDD 原则

本项目使用工程级 TDD 流程，不仅仅是代码级的红-绿-重构。

所有核心业务逻辑、状态机、协议解析、AI 过滤逻辑、固件控制逻辑、App 流程逻辑都必须先写测试。

## 2. 工程级 TDD 流程

### 2.1 需求红：先明确 PRD 验收标准
- 阅读相关 PRD
- 明确验收标准
- 确认非目标
- 确认涉及模块

### 2.2 协议红：先定义协议契约
- 定义 Protobuf / OpenAPI 契约
- 注册 max + min 编号
- 更新协议编号注册表
- 更新 OpenAPI 映射

### 2.3 测试红：先写失败测试
- 编写单元测试
- 编写集成测试
- 编写契约测试
- 编写边界测试
- 测试必须先失败，且失败原因符合预期

### 2.4 实现绿：写最小实现
- 只写让当前测试通过的最小代码
- 不得顺手实现未来功能
- 不得引入不必要抽象
- 不得修改测试含义
- 不得扩大 Issue 范围

### 2.5 报告绿：输出测试报告和证据
- 运行所有测试
- 生成测试报告
- 输出 Standalone HTML 报告
- 截图和视频证据

### 2.6 CI 绿：GitHub Actions 通过
- 推送代码触发 CI
- 所有 CI Job 必须通过
- 如果 CI 无法运行，提供本地等价命令和结果
- 没有测试命令、测试结果、CI 结果，不得宣称完成

### 2.7 重构：测试与 CI 通过后再优化
- 外部行为不变
- 测试全部通过
- CI 全部通过
- 命名更清晰
- 结构更简单
- 重复更少
- 不引入无关依赖

### 2.8 沉淀：日报、Markdown 蒸馏、LLM Wiki 更新
- 提交日报
- Markdown 蒸馏
- 更新 LLM Wiki

## 3. 完成标准

没有 CI 通过或本地等价测试结果，不得宣称任务完成。

如果 CI 暂时无法运行，必须说明：
- 无法运行原因
- 本地等价命令
- 本地结果
- 后续补齐计划

## 4. 测试类型

根据模块选择测试类型：

- AI 模块：单元测试、参数化测试、安全用例测试
- 固件模块：状态机测试、Mock 硬件测试、协议解析测试
- App 模块：状态机测试、ViewModel 测试、流程测试
- 协议模块：序列化、反序列化、兼容性测试、契约测试
- 集成模块：端到端流程测试
- CI 模块：协议唯一性检查、文档检查、报告检查

## 5. 禁止行为

不得：

- 先写实现再补测试
- 删除测试来通过构建
- 只测正常路径，不测异常路径
- 用 Mock 跳过核心逻辑
- 让测试依赖真实外部服务
- 在单元测试中直接调用真实大模型接口
- 没有 CI 结果就宣称完成
- 静默跳过 CI 检查项而不说明原因

## 6. CI 检查要求

每个开发任务必须考虑以下 CI 检查：

| Job | 作用 | 要求 |
|---|---|---|
| `docs-check` | 检查关键文档是否存在 | 必须通过 |
| `proto-check` | 检查协议编号唯一性和注册表同步 | 必须通过 |
| `go-test` | 运行 Golang 测试 | 通过或说明跳过原因 |
| `python-test` | 运行 Python 测试 | 通过或说明跳过原因 |
| `web-test` | 运行 ReactJS App 测试 | 通过或说明跳过原因 |
| `admin-web-test` | 运行 AdminWeb 测试 | 通过或说明跳过原因 |
| `report-check` | 检查测试报告、日报、蒸馏、LLM Wiki | 必须通过 |
