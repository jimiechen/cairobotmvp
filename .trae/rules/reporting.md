# 任务汇报规则

## 1. 文件定位

本文件定义 CaiRobot MVP 项目的任务汇报、Bug 跟踪、事故上报和项目主控评审机制。

本文件用于约束 Trae、AI 编码助手和开发者在执行任务后的汇报方式。

本文件不描述产品业务规则，不替代 PRD、ADR、API 文档或测试文档。

## 2. 协作角色

本项目采用项目主控双评审机制。

### 2.1 项目主控

项目主控分为：

- 项目主控 A
- 项目主控 B

项目主控负责：

- 拆解需求。
- 审查任务范围。
- 判断优先级。
- 审查 Trae 输出。
- 判断风险和事故等级。
- 决定是否继续、回滚、重做或拆分任务。
- 审查 PR 是否可以进入下一阶段。

### 2.2 Trae

Trae 是任务执行者。

Trae 负责：

- 按 Issue 执行任务。
- 按 PRD 和 ADR 理解需求。
- 按 TDD 编写测试和实现。
- 按规范修改文件。
- 运行测试。
- 汇报进度。
- 上报 Bug、事故、风险和阻塞事项。

Trae 不得：

- 自行决定产品方向。
- 自行扩大 Issue 范围。
- 自行修改核心架构。
- 隐瞒失败测试。
- 隐瞒 Bug。
- 隐瞒事故。
- 用“已完成”替代详细汇报。
- 在重大异常后自行继续开发而不上报。

## 3. 汇报原则

所有汇报必须满足：

- 真实。
- 具体。
- 可追溯。
- 可验证。
- 有文件路径。
- 有测试结果。
- 有风险说明。
- 有未完成事项。

不得使用模糊表述，例如：

- “已优化代码。”
- “修复了一些问题。”
- “测试基本通过。”
- “应该没问题。”
- “后续再看。”

必须写清楚：

- 优化了什么。
- 修复了什么。
- 哪些测试通过。
- 哪些测试失败。
- 哪些问题未解决。
- 哪些事项需要主控确认。

## 4. 每日汇报机制

### 4.1 汇报时间

Trae 每天必须在 22:00 前提交日报。

如果当天没有代码变更，也必须提交“无代码变更日报”。

如果当天发生事故，不得等到 22:00，必须立即提交事故报告。

### 4.2 日报接收对象

日报必须发送给：

- 项目主控 A
- 项目主控 B

### 4.3 日报内容

每份日报必须包含：

1. 日期。
2. 当前分支。
3. 当前 Issue。
4. 今日完成内容。
5. 修改文件清单。
6. 新增测试清单。

8. 测试结果。
9. Bug 列表。
10. 事故说明。
11. 风险事项。
12. 阻塞事项。
13. 明日计划。

## 5. Bug 跟踪机制

### 5.1 Bug 定义

以下情况均视为 Bug：

- 功能行为不符合 PRD。
- 实现行为不符合 ADR。
- 测试失败。
- 状态机迁移错误。
- 协议输入输出不一致。
- 边界条件处理错误。
- 异常路径未处理。
- 文档与实现不一致。
- 代码生成了无关行为。
- 修复一个问题导致另一个问题。

### 5.2 Bug 严重等级

Bug 分为四级：

| 等级 | 定义 | 处理要求 |
|---|---|---|
| P0 | 阻断开发、破坏核心流程、导致数据丢失或严重安全风险 | 立即停止相关开发并上报 |
| P1 | 影响核心功能，但存在临时规避方式 | 当天必须处理或给出方案 |
| P2 | 影响局部功能，不阻断主流程 | 排入近期修复计划 |
| P3 | 文案、格式、轻微体验或低风险问题 | 可延后处理 |

### 5.3 Bug 记录格式

每个 Bug 必须记录：

```text

相关 PRD：

期望行为：
实际行为：
影响范围：
初步原因：
修复方案：
验证方式：
是否需要主控确认：
```

### 5.4 Bug 修复规则

修复 Bug 必须遵守：

1. 先创建或关联 Issue。
2. 先写能复现 Bug 的失败测试。
3. 确认测试失败原因符合预期。
4. 编写最小修复代码。
5. 运行相关测试。
6. 确认测试通过。
7. 更新 Bug 状态。
8. 在日报中说明。

不得：

- 直接改代码但不补测试。
- 删除失败测试。
- 修改测试含义来掩盖 Bug。
- 只在日报中说“已修复”，但不说明验证方式。
- 修复 Bug 时顺手做无关重构。

## 6. 事故上报机制

### 6.1 事故定义

以下情况视为事故：

- 误删文件或目录。
- 覆盖重要文档。
- 破坏仓库结构。
- 大量生成无关代码。
- 擅自修改 PRD 范围。
- 擅自修改 ADR 决策。
- 擅自引入重大依赖。
- 绕过 TDD 流程直接实现核心功能。
- 测试大面积失败。
- 提交无法解释的变更。
- 泄露敏感配置或密钥。
- 破坏 Git 历史。
- 错误合并分支。
- 修改与当前 Issue 无关的大量文件。

### 6.2 事故等级

事故分为四级：

| 等级 | 定义 | 处理要求 |
|---|---|---|
| S0 | 严重破坏仓库、数据、密钥或核心文档 | 立即停止所有开发并上报 |
| S1 | 破坏核心模块或核心流程，需要回滚或主控决策 | 立即上报并等待指令 |
| S2 | 影响局部模块，可通过修复恢复 | 当天上报并修复 |
| S3 | 轻微流程违规或低风险异常 | 日报中记录并改进 |

### 6.3 事故立即上报规则

发生 S0、S1、S2 事故时，Trae 必须立即停止当前任务，并提交事故报告。

在项目主控确认前，不得继续扩大修改范围。

## 7. 风险上报机制

### 7.1 风险定义

以下情况必须作为风险上报：

- 需求不清楚。
- PRD 与 Issue 冲突。
- ADR 与实现冲突。
- 测试环境缺失。
- 外部依赖不确定。
- 硬件接口未确认。
- 协议字段未确认。
- 文件规模可能超限。
- 任务范围可能过大。
- 需要新增依赖。
- 需要改变目录结构。
- 需要改变架构边界。

### 7.2 风险等级

风险分为：

| 等级 | 定义 | 处理要求 |
|---|---|---|
| R0 | 不确认就不能继续 | 必须等待主控确认 |
| R1 | 可继续局部工作，但不能合并 | 日报中重点标记 |
| R2 | 对当前任务影响较小 | 日报中记录 |
| R3 | 仅提醒事项 | 可作为备注 |

### 7.3 风险记录格式

```text

```

## 8. 阻塞事项处理

### 8.1 阻塞定义

以下情况属于阻塞：

- 缺少 PRD。
- 缺少 ADR。
- 缺少 Issue。
- 缺少测试环境。
- 依赖无法安装。
- 构建无法运行。
- 硬件信息缺失。
- 接口字段未定义。
- 主控未确认关键决策。
- 权限不足。

### 8.2 阻塞处理规则

遇到阻塞时，Trae 必须：

1. 停止扩大实现范围。
2. 记录阻塞原因。
3. 提供最小可继续任务建议。
4. 在日报中列出。
5. 如果阻塞影响当天任务完成，必须提前上报。

不得：

- 在需求不清楚时自行猜测实现。
- 在 ADR 缺失时自行决定架构。
- 在测试环境缺失时跳过测试并宣称完成。
- 用 TODO 替代 P0 或 P1 阻塞。

## 9. 项目主控评审机制

### 9.1 评审输入

项目主控评审时，Trae 必须提供：

- 当前 Issue。
- 相关 PRD。
- 相关 ADR。
- 修改文件清单。
- 测试命令。
- 测试结果。
- Bug 列表。
- 风险事项。
- 事故报告，如果有。
- 待确认问题。

### 9.2 评审结论

项目主控评审结论分为：

```text
可继续
需要修改
需要补测试
需要补文档
需要拆分任务
需要回滚
需要暂停
```

### 9.3 评审后动作

Trae 必须根据评审结论行动。

不得：

- 忽略主控评审意见。
- 在“需要暂停”时继续开发。
- 在“需要回滚”时继续叠加修改。
- 在“需要补测试”时直接进入下一任务。
- 在“需要补文档”时直接宣称任务完成。

## 12. 禁止行为

Trae 不得：

- 不提交日报。
- 用一句话代替日报。
- 隐瞒测试失败。
- 隐瞒 Bug。
- 隐瞒事故。
- 隐瞒未完成事项。
- 未经确认自行扩大任务范围。
- 未经确认自行修改架构。
- 未经确认自行新增大型依赖。
- 未经确认自行删除文件或目录。
- 事故发生后继续扩大修改范围。
- 将未运行测试写成测试通过。
