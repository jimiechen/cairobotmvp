## 三、必须修改项（P0 阻断问题）

### ❌ **问题 1：MessagePacket.data 格式与当前实现冲突**

**严重等级：P0（阻断项）**
**影响范围：架构核心**

**方案描述：**
```text
MessagePacket.data 承载 JSON payload
JSON payload 的字段语义由 Protobuf message 定义
业务模块接收 JSON DTO 或 Protobuf message 对齐对象
```

**当前实现：**
```go
// SystemService 返回 Protobuf bytes
func (s *SystemService) HealthCheck(ctx context.Context, serviceName string) ([]byte, error) {
    resp := &pb.ServiceHealthCheckResponse{...}
    return proto.Marshal(resp)  // 返回 Protobuf 序列化的 bytes
}

// LocalHandler 直接透传 bytes
func (h *Handler) Invoke(ctx context.Context, request []byte, extend map[string]string) (int, []byte, error) {
    respBytes, err := h.service.HealthCheck(ctx, "")
    return 10200, respBytes, nil  // 直接返回 Protobuf bytes
}

// Gateway 直接传递 data
returnCode, responseBytes, err := gs.invoker.Invoke(r.Context(), target, packet.Data, extend)
```

**冲突点：**

| 维度 | 方案要求 | 当前实现 |
|---|---|---|
| data 格式 | UTF-8 JSON | Protobuf binary |
| 模块接口 | JSON DTO 或 Protobuf 对象 | `[]byte` (Protobuf bytes) |
| 编解码责任 | Gateway 负责 JSON ↔ DTO | Service 自己 Marshal/Unmarshal |
| 测试方式 | 直接构造 DTO | 构造 Protobuf bytes |

**必须决策：**

**选项 A：按方案改为 JSON payload**
- ✅ 符合方案设计意图
- ✅ 调试友好，可读性强
- ✅ 前端对接简单
- ❌ 需要重构现有代码
- ❌ 失去 Protobuf 二进制效率优势
- ❌ 需要重新验证 Tars 兼容性

**选项 B：保持 Protobuf bytes，调整方案描述**
- ✅ 无需重构现有代码
- ✅ 保持二进制效率
- ✅ 已通过初步验证
- ❌ 与方案描述不一致
- ❌ 调试相对复杂

**建议：**
1. **立即决策**采用哪种格式
2. 如果选 A，需要补充迁移计划和兼容性策略
3. 如果选 B，需要修正方案中关于 JSON payload 的描述
4. 无论哪种选择，必须在 ADR 中记录决策理由

### ⚠️ **建议 1：模块接口定义需要更具体**

**严重等级：P1**
**当前方案：**

```go
type HelloService interface {
    SayHello(ctx context.Context, req Request) (Response, error)
}
```

**问题：**
- `Request` 和 `Response` 类型未明确定义
- 缺少错误码约定
- 缺少上下文传递规范（traceId、requestId 等）

**建议补充：**

```go
// HelloService HelloWorld 模块接口
// 业务模块不依赖 MessagePacket，只接收 Protobuf 对齐的 DTO
type HelloService interface {
    // SayHello 执行问候操作
    // ctx 携带 traceId、requestId 等链路信息
    // req 包含请求参数（name 字段）
    // 返回响应 DTO 和 nil 表示成功
    // 返回 nil 和 error 表示业务失败
    SayHello(ctx context.Context, req *HelloWorldRequest) (*HelloWorldResponse, error)
}

// HelloWorldRequest HelloWorld 请求 DTO
// 字段语义对齐 proto/base/hello.proto 中的 HelloWorldRequest
type HelloWorldRequest struct {
    Name string `json:"name"` // 可选名称，为空时返回默认问候语
}

// HelloWorldResponse HelloWorld 响应 DTO
// 字段语义对齐 proto/base/hello.proto 中的 HelloWorldResponse
type HelloWorldResponse struct {
    Result    *ResultDTO `json:"result"`    // 统一结果码
    Message   string     `json:"message"`   // 问候消息文本
    Timestamp int64      `json:"timestamp"` // Unix 时间戳
}
```

### ⚠️ **建议 2：JSON vs Protobuf 性能影响评估缺失**

**严重等级：P1**

**方案选择 JSON payload 的潜在影响：**

| 维度 | JSON | Protobuf Binary |
|---|---|---|
| 序列化速度 | 较慢（字符串解析） | 快（二进制编码） |
| 数据体积 | 较大（字段名重复） | 小（Varint 编码） |
| 可读性 | 高（可直接查看） | 低（需要工具解析） |
| 前端对接 | 简单（原生支持） | 需要 protobuf.js |
| Schema 演进 | 弱类型（易出错） | 强类型（编译检查） |
| Tars 兼容性 | 需要转换层 | 原生支持 |

**建议补充：**

1. **性能基准测试**：对比 JSON 和 Protobuf 在典型场景下的吞吐量
2. **Tars 兼容性分析**：确认 TarsGo 是否原生支持 JSON 传输
3. **前端对接成本**：评估前端使用 protobuf.js 的学习曲线
4. **最终建议**：基于数据给出推荐，而非主观选择
