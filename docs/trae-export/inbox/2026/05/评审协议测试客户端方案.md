## 三、必须修改项 🔴

### 修改 1：【P1】protobuf.js 与现有 google-protobuf 技术栈冲突

**问题描述**：

现有 [typescript/web/package.json](typescript/web/package.json#L16) 已使用 `google-protobuf`（预生成 TS 代码方案），同时 devDependencies 中也有 `protobufjs`（^7.2.6）。方案要求 proto-tester 使用 `protobuf.js 运行时解析`，但：

1. **同一 monorepo 内两套 Protobuf 运行时**会增加维护复杂度和包体积
2. protobuf.js v7 的 CommonJS/ESM 兼容性问题在 Vite 5 下已有大量 issue
3. 现有 [proto-client.ts](typescript/web/src/utils/proto-client.ts#L12-L18) 已封装了基于 `google-protobuf` 的 `MessagePacket` 构建/解析逻辑，proto-tester 应复用而非重写

**证据**：

```typescript
// typescript/web/src/utils/proto-client.ts (已有实现)
import { com as messageCom } from '@proto/base/message';
const { mineplanet: { pojo: { MessagePacket, Platform } } } = messageCom;
// → 已经能 buildPacket / postGateway / deserializeBinary
```

**建议方案**（二选一）：

| 方案 | 做法 | 优缺点 |
|---|---|---|
| A. 统一用 google-protobuf | proto-tester 也用 `@proto/*` 预生成代码，构建期同步生成 | ✅ 与现有一致；❌ 改 proto 后需重新生成 |
| B. 保持 protobuf.js 但隔离 | proto-tester 独立使用 protobuf.js，不引入 workspace 共享依赖 | ✅ 运行时灵活；❌ 双运行时维护成本 |

**如果坚持方案 B**，必须在 T0 阶段明确说明选择理由并增加兼容性验证任务。

### 修改 3：【P1】protoFormBuilder.ts 示例代码存在 proto3 语义错误

**问题描述**：

方案 §3.3 给出的示例代码：

```typescript
// 方案原文 (第 156 行)
required: field.required,
```

**proto3 中不存在 `field.required`**。proto3 的所有字段都是 optional，无法通过 `field.required` 判断必填。这是 protobuf.js 的 API 误用。

**正确的做法**应为以下之一：
- 通过 oneof 包装判断必填（方案自己提到了但代码未体现）
- 通过字段注释约定（如 `(required)` 注解）
- 通过协议元数据 protocols.json 的 `authRequired` 字段派生

此外，`field.comment` 在 protobuf.js 中取的是 JSDoc 注释，不是 proto 注释。proto 文件中的注释需要特殊配置才能读取。

**要求**：修正示例代码，补充 proto3 必填判定策略。

## 四、建议修改项 🟡

### 建议 1：【P2】extend 字段定义与 message.proto 不完全对齐

**现状对比**：

| 方案描述 | message.proto 实际定义 | 差异 |
|---|---|---|
| "标准 16 字段" | `map<string, string> extend = 3`（无字段数限制） | "16 字段"说法无依据 |
| 自动填充 `requestProto / responseProto` | MessagePacket 无此字段 | 需放入 extend map |
| 自动填充 `authRequired / auditRequired` | MessagePacket 无此字段 | 需放入 extend map |

**建议**：将"16 字段"改为"CODE-WIKI 约定的 extend key 集合"，并引用具体文档。`requestProto`/`responseProto`/`authRequired`/`auditRequired` 明确标注为 extend map 的 key，而非 MessagePacket 的独立字段。

### 建议 4：【P3】动态枚举拉取协议号可能有误

**问题**：

§3.4 提到"通过 6001 协议拉取动态枚举"。6001 是 `AppConfigsReq`（获取全量应用配置），用它来拉取 module_key 动态枚举虽然数据上可行（AppConfigsRsp.dynamic_modules 包含 module_key 列表），但语义上是"拿配置数据当枚举用"，可能导致：

1. 数据量大（全量配置 vs 仅枚举列表）
2. 缓存策略不当（5 分钟缓存配置 vs 枚举可能变化频率不同）
3. 权限问题（获取配置可能需要更高权限）

**建议**：明确动态枚举的数据来源契约，或考虑单独的枚举查询接口。

---

### 建议 5：【P3】Zustand localStorage 持久化中间件需明确版本

**问题**：

方案多处提到 Zustand + localStorage 持久化，但未指定使用的持久化中间件（如 `zustand/middleware` 的 `persist`）。不同版本的 persist 中间件在迁移、部分持久化（不持久化 token）方面的行为差异较大。

**建议**：T0.1 依赖清单中明确 `zustand` 版本和 `persist` 中间件版本。

---

### 建议 6：【P3】IndexedDB 容量上限 1000 条可能不够

**问题**：

对于高频联调场景，1000 条 LRU 上限可能在 1-2 天内爆满。且 IndexedDB 清理策略（LRU 实现）本身有一定复杂度。

**建议**：
- 考虑按时间窗口（如最近 7 天）而非固定条数
- 或提供"导出/清理"功能入口
- 补充 LRU 实现的技术选型（手写 vs idb-keyval 等库）
