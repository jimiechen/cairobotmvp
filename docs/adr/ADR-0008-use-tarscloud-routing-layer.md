# ADR-0008: 使用 TarsCloud 作为 Protobuf 到 TarsGo 的内部路由转发层

## 1. 基本信息

| 字段 | 值 |
|------|-----|
| ID | ADR-0008 |
| 名称 | 使用 TarsCloud 作为 Protobuf 到 TarsGo 的内部路由转发层 |
| 状态 | 草稿 |
| 创建日期 | 2026-05-18 |
| 最后更新 | 2026-05-18 |
| 创建人 | 项目团队 |

## 2. 背景

CaiRobot MVP 初期架构采用纯 gRPC + Protobuf 方案，内部服务直接通过 gRPC 调用。随着项目演进，发现存在以下问题：

1. 缺少完整的服务治理能力，如服务注册、服务发现、负载均衡、熔断、监控等。
2. 网关层需要直接感知具体业务服务，增加了耦合度。
3. 内部服务调用链路不够清晰，运维和排查问题困难。
4. 灰度发布、容量规划等高级能力缺失。
5. gRPC 虽然是优秀的 RPC 框架，但在微服务治理能力上不够完整。

TarsCloud 是腾讯开源的高性能微服务框架，提供了完整的服务治理、监控、配置等能力，并且支持多语言。同时，TarsGo 作为 Go 语言的 Tars 实现，具有高性能、易用等特点。

## 3. 决策

CaiRobot MVP 采用 Protobuf 作为统一接口契约来源，同时引入 TarsCloud 作为内部服务治理与路由转发框架。外部请求通过 API Gateway 或 Proto Gateway 接入后，由 TarsCloud 路由层根据 Protobuf package、service、method 或协议编号映射到内部 TarsGo servant。内部核心业务服务采用 TarsGo 实现，并通过 TarsCloud 获得服务注册、服务发现、负载均衡、超时控制、监控、灰度发布等治理能力。

具体决策要点：

1. **协议契约层**：Protobuf 仍然是唯一的外部与跨语言接口契约来源。
2. **外部接入**：对外可以通过 grpc-gateway 暴露 HTTPS JSON，也可以直接接收 gRPC/Protobuf。
3. **路由转发层**：TarsCloud 路由层负责将 Protobuf 请求转发到内部 TarsGo 服务。
4. **内部服务**：核心业务服务采用 TarsGo 实现。
5. **职责边界**：Gateway 不直接耦合具体业务服务，通过协议编号、服务名、方法名或路由配置转发。

## 4. 理由

### 4.1 为什么选择 TarsCloud

1. **完整的微服务治理能力**：TarsCloud 提供了服务注册、发现、负载均衡、熔断、降级、限流、灰度发布、监控等完整能力。
2. **高性能**：TarsGo 基于 Go 语言，性能优秀，适合高并发场景。
3. **多语言支持**：Tars 支持 C++、Java、Go、Python、Node.js 等多种语言，未来扩展方便。
4. **成熟稳定**：TarsCloud 在腾讯内部大规模使用，经过实战验证。
5. **开源社区活跃**：有活跃的社区支持和持续的更新维护。
6. **可视化运维**：提供了 Web 管理界面，便于运维和监控。

### 4.2 与 gRPC / Protobuf 的关系

1. **Protobuf 仍然是契约来源**：对外接口、文档、SDK 都基于 Protobuf 生成，保持一致性。
2. **gRPC 作为外部接入方式**：外部系统可以通过 gRPC 或 HTTPS JSON（通过 grpc-gateway）接入。
3. **Tars 作为内部通信方式**：内部服务之间使用 Tars 协议通信，获得更好的服务治理能力。
4. **协议转换在 Gateway 层完成**：Proto Gateway 负责将 Protobuf 请求转换为 Tars 调用，反之亦然。

这种架构设计实现了：
- 外部兼容性：保持 Protobuf 作为统一契约，便于第三方系统接入。
- 内部可控性：使用 TarsCloud 提供完整的服务治理能力。
- 清晰的职责边界：Gateway 只做协议转换和路由，不承载业务逻辑。

## 5. 替代方案

### 5.1 方案一：纯 gRPC + etcd/consul

- **优点**：技术简单，gRPC 生态成熟。
- **缺点**：缺少完整的服务治理能力，需要自己实现熔断、监控、灰度等功能，运维成本高。

### 5.2 方案二：Istio + gRPC

- **优点**：Service Mesh 能力强大，与语言无关。
- **缺点**：架构复杂，运维成本高，性能有一定损耗，学习曲线陡峭。

### 5.3 方案三：Dubbo-go

- **优点**：国内使用广泛，与 Java 生态集成好。
- **缺点**：Go 版本相对较新，社区活跃度不如 TarsGo，多语言支持较弱。

### 5.4 方案四：保持现状，纯 gRPC

- **优点**：无需改动，快速落地。
- **缺点**：长期来看，服务治理能力缺失会成为瓶颈，运维成本会越来越高。

经过对比，选择 TarsCloud 作为内部服务治理框架。

## 6. 后果

### 6.1 正面影响

1. **服务治理能力提升**：获得完整的服务注册、发现、负载均衡、熔断、监控等能力。
2. **运维效率提升**：提供可视化的管理界面，便于运维和监控。
3. **架构解耦**：Gateway 与业务服务解耦，便于扩展和维护。
4. **灰度发布支持**：可以方便地实现灰度发布，降低发布风险。
5. **性能保障**：TarsGo 性能优秀，适合高并发场景。

### 6.2 负面影响

1. **技术栈复杂度增加**：引入新的框架，团队需要学习成本。
2. **协议转换开销**：Gateway 层需要进行 Protobuf 与 Tars 协议的转换，有一定的性能损耗。
3. **部署复杂度增加**：需要部署 TarsCloud 管理平台，增加了运维复杂度。
4. **初期工作量增加**：需要搭建 TarsCloud 环境，实现 Gateway 层的协议转换。

### 6.3 风险与缓解措施

| 风险 | 影响 | 可能性 | 缓解措施 |
|------|------|--------|----------|
| 团队学习成本高 | 中 | 中 | 提供培训文档，先在非核心服务上试点 |
| 协议转换性能损耗 | 低 | 中 | 进行性能测试，必要时优化转换逻辑 |
| 部署复杂度增加 | 中 | 中 | 提供自动化部署脚本，容器化部署 |
| 初期工作量大 | 中 | 高 | 分阶段实施，先搭建框架，再迁移服务 |

## 7. 约束

1. **Protobuf 契约优先**：所有接口定义必须先在 proto/ 目录中定义，作为唯一的契约来源。
2. **Gateway 不承载业务逻辑**：Proto Gateway 只做协议解析、路由转发、上下文透传，不承载业务逻辑。
3. **TarsGo 服务必须注册到 TarsCloud**：所有内部 TarsGo 服务必须在 TarsCloud 注册，通过 TarsCloud 进行服务治理。
4. **错误码统一转换**：内部 Tars 错误必须转换为统一的 Protobuf Result 响应，不暴露底层错误细节。
5. **链路追踪必须贯穿**：所有调用必须包含 trace-id，便于问题排查。

## 8. 后续待确认事项

1. **具体的 TarsGo Web 框架**：是否需要在 TarsGo 之上再封装 Web 框架，还是直接使用 TarsGo 的能力。
2. **数据库访问层**：TarsGo 服务的数据库访问方式，是使用 ORM 还是原生 SQL。
3. **配置管理**：TarsCloud 的配置管理如何与现有配置管理集成。
4. **监控告警**：TarsCloud 的监控如何与现有监控系统集成。
5. **日志聚合**：TarsGo 服务的日志如何统一收集和分析。
6. **灰度发布策略**：具体的灰度发布规则和流程。
