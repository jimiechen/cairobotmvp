### 2.2 需主控确认项（评审阻断点）

1. **R0-依赖引入**：LangGraph（含 langchain-core）属大型依赖，按规则需先立 ADR（建议 ADR-017），评审通过后方可进入实现。
2. **R0-术语确认**："agent-plan 外接大模型"在本 PRD 中解释为：**Planner 采用 Plan-and-Execute（计划-执行）模式，大模型通过 OpenAI 兼容 API 外部接入**（base\_url / api\_key / model 全部配置化，不内置本地模型，不在代码中硬编码密钥）。如与主控意图不符，需在评审时修正。
3. **R1-目录位置**：服务代码建议落位 `python/ai/fa_orchestrator/`（与 hello 同级，遵循 ADR-0012）；`docs.md` 目录约束写的是 `ai/`，两处以哪份为准需主控裁决。

## 3. 背景

FA 竞彩分析当前以 `.trae/skills/fa-football-analyst`（v7.12）对话式 Skill 运行：分析师在对话中人工触发，按两阶段分析法逐场分析。存在四个问题：

1. **人工编排**：取数 → 完整性核查 → 缺口补抓 → 逐场分析 → 复盘，全部由人在对话内驱动，效率低、易漏步骤（v7.10-v7.12 多次修订均因人工执行规则遗漏导致误判）。
2. **规则执行不可度量**：反大众前置检查、撤离信号硬门槛、七项矛盾检查等纪律条款依赖模型自觉遵守，无法保证 100% 执行。
3. **过程不可追溯**：分析结论依赖哪些数据块、经过哪些规则分支，事后难以精确复现，复盘定位困难。
4. **单场串行**：7 场比赛串行分析，无法并行，也无中间态缓存与断点续跑。

同时，上游《局域网数据获取》需求文档已将数据通道标准化（MySQL 直连 / HTTP API / Skill 补抓三通道 + Q1-Q14 固化 SQL），为编排系统的取数层提供了稳定契约。

## 4. 目标

1. 基于 LangGraph 构建 FA-Orchestrator：以 StateGraph 将 fa-football-analyst v7.12 两阶段分析法落地为 8 类可编排 Agent 节点，一条命令完成"指定竞彩日 → 数据准备 → 逐场分析 → 报告产出"端到端流程。
2. **可视化编排**：图结构以编排配置（YAML）定义，支持 Mermaid 图导出与运行轨迹渲染；节点可增删、条件分支可调，无需改核心代码。
3. **可追溯工作流**：每场比赛一个 thread；checkpointer 持久化节点级输入/输出/耗时/数据来源（数据块编号 D1-D12 + 通道 + 快照时间）；支持断点恢复与轨迹回放。
4. **纪律条款节点化强制执行**：反大众前置检查、撤离信号≥3重硬门槛、推荐结构互斥、七项矛盾检查均实现为显式图节点/条件边，保证 100% 执行且结果落盘。
5. **agent-plan 模式接入大模型**：Planner 生成并动态修订分析计划；所有大模型调用走统一网关（OpenAI 兼容 API，配置化接入），单元测试一律 Mock，禁止真实调用。

## 5. 非目标

* 不修改、不替换 `.trae/skills/fa-football-analyst` Skill 本身（本期 Orchestrator 以该 Skill 规范为行为基准，Skill 保留作为对话式入口）。

* 不修改 ETL 管道、爬虫脚本与 python-server（外部 game-crawler 项目，本系统只做数据消费端）。

* 不做投注执行、资金对接、实盘下单。

* MVP 不做 Web 图形化拖拽编排编辑器（仅 Mermaid 导出 + 轨迹渲染，编辑器列入遗留事项）。

* 不新增 Protobuf 协议（MVP 入口为 CLI；后续如开放 gRPC/HTTP 对外接口，须先走协议编号注册表流程）。

* 不解决需求文档"遗留事项"章节问题（D9 变盘史无独立表、checkGate 口径不匹配等，维持上游结论）。

## 7. 核心流程

```text
PlannerAgent（agent-plan，外接大模型）
  ① 输入竞彩日 → 生成分析计划（场次清单、数据预检结论、补抓指令、并行分组）
        ↓
DataAgent（每场一个子图实例，可并行）
  ② Q1 拉清单 → fid→match.id 解析 → Q2b 六模块完整性核查
  ③ 缺口 → 按 D1-D12 映射走 HTTP API / Skill 补抓 → ETL 重跑 → 复核
        ↓
FundamentalAgent（基本面 50%）          OddsVerifyAgent（赔率验证 50%）
  ④ 情报 30% / 初盘 25% /                 ④ 赔率结构 / 欧亚转换（升盘解读、
     交锋 15% / 状态 20% / 赛程 10%           两层背离）/ 热度验证 / 异常信号
  ⑤ 进球外推 + 杯赛/国际赛修正             ⑤ 防冷分级、立博独开分流、单家背离
        ↓                                      ↓
SentimentAgent（热度与人性）── 支持率偏差、过热场分档、必发形态
        ↓
SynthesisAgent（综合判定）
  ⑥ 反大众前置检查 → 撤离信号硬门槛 → 推荐结构互斥 → 低赔补位条款
        ↓
ReviewAgent（矛盾检查，条件回退）
  ⑦ 七项一致性检查 ──不通过──→ 回退 SynthesisAgent 修订（最多 2 次，仍不过则人工裁决）
        ↓ 通过
ReportAgent
  ⑧ 按 OUTPUT_TEMPLATE.md 出报告 + 数据溯源声明（模式 + 数据块 + 快照时间）
```

## 8. 功能需求

### 8.1 P0 — 编排内核

| 编号   | 需求              | 说明                                                                                               |
| ---- | --------------- | ------------------------------------------------------------------------------------------------ |
| F-01 | StateGraph 编排内核 | 图拓扑由 YAML 编排配置定义（节点、边、条件分支、重试次数）；核心代码不硬编码图结构                                                     |
| F-02 | PlannerAgent    | Plan-and-Execute：产出结构化分析计划（场次、并行分组、数据预检、补抓清单）；执行中可 Re-Plan（数据缺口/检查拦截触发）                          |
| F-03 | LLM 统一网关        | OpenAI 兼容 API 外接大模型；`base_url/api_key/model/temperature` 全配置化（环境变量注入）；密钥不落代码、不记日志；统一超时/重试/降级     |
| F-04 | 多场并行执行          | 同竞彩日多场次按计划分组并行，单场失败不影响其他场次                                                                       |
| F-05 | CLI 入口          | `run --date`（日级全流程）/ `replay --thread-id`（轨迹回放）/ `graph`（Mermaid 导出）/ `show --thread-id`（节点轨迹查看） |

### 8.2 P0 — 数据层（DataAgent）

| 编号   | 需求      | 说明                                                                                          |
| ---- | ------- | ------------------------------------------------------------------------------------------- |
| F-06 | 三通道取数工具 | 按需求文档 §2/§4 封装：MySQL 直连（Q1-Q14 参数化 SQL）、HTTP API（§5.3 接口）、Skill 补抓指令下发                      |
| F-07 | ID 解析   | 实现 fid → match.id 落点逻辑（场次编号+日期窗口 → 场次编号 → 队名归一兜底），遵守 `match` 反引号、跨日窗口等口径约束                  |
| F-08 | 完整性核查   | Q2b 六模块（ouzhi/yazhi/daxiao/vote/stats/intel）行数核查；不完整触发补抓子流程；补抓失败必须落 error/blocked 状态，禁止静默跳过 |
| F-09 | 数据溯源快照  | 每次取数记录：数据块编号（D1-D12）、通道、SQL/接口标识、快照时间、行数，写入运行轨迹                                             |

### 8.3 P0 — 分析层（四类分析 Agent）

| 编号   | 需求               | 说明                                                                                               |
| ---- | ---------------- | ------------------------------------------------------------------------------------------------ |
| F-10 | FundamentalAgent | 情报分析（7M 利弊比量化 + 均势约束）、初盘定位（同盘路历史）、历史交锋、近期状态（进球数外推，杯赛/国际赛修正条款）、赛程影响；权重按 v7.12                     |
| F-11 | OddsVerifyAgent  | 赔率结构验证、欧亚转换（升盘真信号边界条件、两层背离信让球层）、市场热度验证（过热场分档处置）、异常信号排查（防冷分级、立博独开分流、单家临场背离）                       |
| F-12 | SentimentAgent   | 投票支持率偏差计算（HAD/HHAD）、过热判定（≥+20pp / 让球 ≥+15pp）、必发成交形态输入                                            |
| F-13 | SynthesisAgent   | 反大众前置检查（①②③锚点 + 时效衰减 + 语义解耦）、撤离信号硬门槛（≥3 重强制放弃/双选）、让球单选判定标准、推荐结构互斥（S/D 单元合法性）、低赔补位条款（SP<1.5 路径 C） |

### 8.4 P0 — 质检与输出层

| 编号   | 需求          | 说明                                                                                                     |
| ---- | ----------- | ------------------------------------------------------------------------------------------------------ |
| F-14 | ReviewAgent | 七项矛盾检查（CONSISTENCY\_CHECKS.md v7.12 版）逐项执行；每项结果（通过/命中矛盾/修正动作）落盘；不通过条件回退 SynthesisAgent，最多 2 次，仍不过转人工裁决 |
| F-15 | ReportAgent | 按 OUTPUT\_TEMPLATE.md 输出报告；数据来源声明强制标注模式（MySQL/file）与快照时间；模拟数据检测告警（整数赔率/全同赔/缺主流公司等）                     |
| F-16 | 历史推演接入      | MySQL 模式下调用升降盘时序与投票热度漂移（对应 SKILL v7.4 M5 能力），缺失时明确标注"无法推演时序"                                           |

### 8.5 P1 — 可视化与追溯（M4）

| 编号   | 需求            | 说明                                                                   |
| ---- | ------------- | -------------------------------------------------------------------- |
| F-17 | 图结构可视化        | `graph` 子命令导出当前 StateGraph Mermaid 源码并渲染为图文件                         |
| F-18 | 运行轨迹可视化       | 按场次渲染节点执行时序图（节点状态、耗时、数据来源、条件分支走向）                                    |
| F-19 | Checkpoint 恢复 | SQLite checkpointer；进程中断后可从最近 checkpoint 续跑                          |
| F-20 | 人工裁决点         | ReviewAgent 拦截/数据严重缺失时暂停并输出裁决提示，人工确认后继续（human-in-the-loop interrupt） |

## 14. 验收标准

1. `fa_orchestrator run --date 2026-09-29` 一条命令端到端产出 7 份报告，结构符合 OUTPUT\_TEMPLATE.md（含竞彩让球胜平负预测表、反大众检查表、报告矛盾检查章节）。
2. 每份报告数据溯源声明 100% 覆盖：标注数据模式（MySQL/file）、数据块编号、快照时间；无任何模拟数据告警遗漏。
3. 可追溯：每场 thread 可 `replay` 回放；任意节点输入/输出/耗时/数据来源可查；进程中断后可从 checkpoint 续跑。
4. 纪律条款强制：反人性推荐 100% 经过反大众前置检查节点；撤离信号 ≥3 重的场次 100% 触发放弃/双选分支（以周六012、周日007/008 案例锚点做回归断言）。
5. 七项矛盾检查全部执行且结果写入报告；互斥原则（S/D 单元合法性）由图条件边保证而非提示词自觉。
6. Mermaid 导出与运行时 StateGraph 定义一致（以编排配置为准做一致性断言）。
7. 单元测试全部使用 Mock LLM 与本地 fixture，`python/ai` 子 Makefile `make unit` 通过；`make rules` 六项检查通过。
8. 需求文档 §七 验收标准第 1/3 条（SQL 行数一致、五模块入库行数 > 0）作为数据层前置验收项引用。
