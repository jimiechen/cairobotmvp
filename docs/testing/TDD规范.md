# TDD 规范

## 1. 红-绿-重构流程

本项目要求所有可测试代码必须严格遵守 TDD 红-绿-重构流程。

### 1.1 红阶段

- 先写失败测试
- 测试必须能复现问题或验证需求
- 测试必须明确失败原因符合预期
- 不能先实现再补测试
- 不能删除失败测试

### 1.2 绿阶段

- 写最小实现代码让测试通过
- 实现范围不能超出当前测试覆盖的需求
- 不能顺手实现未来功能
- 不能过度设计

### 1.3 重构阶段

- 测试必须全部通过才能重构
- 重构不能改变外部行为
- 重构可以优化结构、命名、可读性
- 重构后必须再次运行测试

## 2. 需求 -> 用例 -> 代码流程

每个需求必须按以下顺序处理：

1. 需求（PRD/Issue）→ 
2. 测试用例 → 
3. 失败测试 → 
4. 最小实现 → 
5. 测试通过 → 
6. 重构

## 3. 每个需求必须先有测试

以下场景必须先写测试：

- 新增功能
- 修复 Bug
- 重构核心逻辑
- 状态迁移
- 协议解析
- 安全过滤

## 4. 每个 Bug 修复必须先有复现测试

修复 Bug 的标准流程：

1. 写一个能复现 Bug 的失败测试
2. 确认测试失败原因与 Bug 一致
3. 修复 Bug
4. 运行测试确认通过
5. 在日报中说明

## 5. 测试用例要求

每个测试用例必须包含：

- 用例 ID
- 用例名称
- 前置条件
- 测试步骤
- 输入
- 期望输出
- 优先级
- 相关 PRD/Issue
- 证据文件（截图/视频路径）

## 6. 测试报告要求

每次运行测试后必须生成测试报告，包含：

- 测试报告 ID
- 测试日期
- 测试人
- 测试命令
- 测试结果摘要
- 通过/失败用例列表
- 失败原因
- 截图/视频证据
- 日志
- 结论

## 7. 禁止行为

严禁：

- 先写实现再补测试
- 删除失败测试
- 修改测试含义来迁就实现
- 在没有测试的情况下实现 P0/P1 功能
- 用 Mock 掩盖核心业务逻辑
- 跳过测试并宣称完成
