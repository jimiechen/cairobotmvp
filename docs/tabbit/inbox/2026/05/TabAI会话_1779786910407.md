### **以 React 18 + Vite + TypeScript + Ant Design + protobuf.js 构建独立的 proto-tester 工程，核心是「协议元数据驱动 + MessagePacket 自动包装 + 表单按 proto schema 自动渲染 + traceId 全链路贯穿」，所有测试请求严格走 /api/hello + MessagePacket，禁止直连 Tars，禁止绕过 Gateway，禁止把它做成第二个业务客户端。**

下面这套方案给出工程定位、目录结构、6 大核心能力的技术设计、给 Trae 的执行指令，以及与现有 admin-web、业务 web 严格隔离的边界。

---

### **一、定位与边界**

#### **1.1 工程定位**

```text
名称：proto-tester（开发者工具）
位置：typescript/proto-tester/
角色：研发 / QA 内部使用的协议联调工具
对手目标：替代 Postman/Apifox 在 MessagePacket + Protobuf bytes 场景下的不便
```

#### **1.2 严格边界（铁律）**

```text
- 不部署在公网，仅内网研发段可达
- 不接入业务鉴权体系（用 Mock 用户池或 dev-only Token Server）
- 不复用 typescript/web 的业务组件库
- 不依赖 typescript/admin-web 的运维账号
- 不做"伪客户端 SDK"，不替代真实客户端联调
- 仅通过 /api/hello + MessagePacket 走 Gateway，与真实客户端同等待遇
- 不直连 TarsGo Servant、不绕过 routes.yaml
- 不写入业务库（仅本地 IndexedDB 存历史请求）
```

为什么要这条铁律：旧项目内部测试工具最终会被偷偷接到生产，承担"灰度调试"角色，变成第二个不可控入口。proto-tester 必须从设计上就做不到这件事。

---

### **二、技术栈选型**

```text
- React 18 + TypeScript 5
- Vite 5（开发体验、构建速度）
- Ant Design 5（成熟、表单组件齐全、与 admin-web 风格一致但独立部署）
- protobuf.js（运行时解析 .proto，无需提前 codegen）
- Zustand（轻量状态，用于会话/Token/历史）
- React Router 6
- Monaco Editor（JSON 入参/出参展示与编辑）
- axios（HTTP 客户端）
- dayjs / lodash-es 工具
- vitest + @testing-library/react（单元 + 组件测试）
- Playwright（端到端，可选）
- pnpm + pnpm workspace

不引入：
- Redux / MobX（过重）
- 自家的 web 组件库（独立工程，零耦合）
- 任何业务 SDK（避免循环依赖）
```

为什么 protobuf.js 而不是预生成 ts 代码：本工具的核心价值是"研发改完 proto 立刻能调"，预生成会拖累迭代。protobuf.js 直接吃 .proto 文件即可。

### **三、6 大核心能力的技术设计**

#### **3.1 协议选择**

```text
能力：从协议元数据库中按 maxType/minType 选择协议
数据源：
  - 主：从 docs/api/协议编号注册表.md 解析（构建期同步到 protocols.json）
  - 副：从 proto/**/*.proto 反向扫描，列出所有 message 与对应 oneof
存储：assets/protocols.json（构建期生成 + 热更）

UI：
  - 左侧树状导航：按 maxType 分组（2100 系统 / 6000 应用配置 / ...）
  - 节点显示：协议号 + 协议名 + 请求/响应 message 名
  - 搜索框：按协议号或名称模糊搜索
  - 收藏夹：常用协议置顶
```

实现细节：

```ts
// src/data/protocols.ts
export interface ProtocolMeta {
  maxType: number;
  minType: number;
  name: string;
  reqMessage: string;     // e.g. HelloWorldRequest
  rspMessage: string;
  protoFile: string;       // e.g. proto/base/hello.proto
  group: string;           // 系统/配置/i18n/...
  description: string;
  authRequired: boolean;
  deprecated?: boolean;
}
```

#### **3.2 通用参数设置（MessagePacket extend）**

```text
能力：为每次请求设置 MessagePacket 头部参数
字段（与 CODE-WIKI extend map 标准 16 字段一致）：
  必填：traceId / requestId / token / clientVersion / platform
  可选：langCode / userId / tenantId / clientIp / caller
  自动：maxType / minType（从协议选择派生）
        requestProto / responseProto（从 protoFile 派生）
        authRequired / auditRequired（从协议元数据派生）

UI：
  - 顶部固定面板：通用参数全局设置（多协议共用）
  - 每协议页可覆盖：协议级覆盖优先级高于全局
  - traceId / requestId 默认自动生成（UUID v4）
  - 一键重置默认值
```

存储：

```text
- 全局参数：localStorage（user-scoped）
- 当前会话：Zustand session store
- 协议级覆盖：跟随协议表单一同保存
```

#### **3.3 协议参数填充（按 proto schema 自动渲染）**

```text
能力：选定协议后，按 reqMessage 的 proto 定义自动渲染表单
渲染规则：
  - string → input
  - int32 / int64 → number
  - bool → switch
  - bytes → 文件上传 / hex 输入双模式
  - enum → select（自动列出枚举值 + 显示名）
  - repeated → 列表组件（可增删行）
  - nested message → 折叠面板（递归渲染）
  - oneof → tab 选择，仅一个生效
  - map<string, T> → 键值对编辑器

附加：
  - 字段说明 tooltip：从 proto 注释抽取
  - 必填校验：proto3 中通过 oneof 包装或 nullable 注释判定
  - 默认值：从协议元数据 + 注释抽取
  - JSON 模式切换：复杂场景下直接编辑 JSON
```

实现：

```ts
// src/lib/protoFormBuilder.ts
import * as protobuf from 'protobufjs';

export function buildFormSchema(
  root: protobuf.Root,
  messageName: string,
): FormFieldSchema[] {
  const Type = root.lookupType(messageName);
  return Type.fieldsArray.map(field => ({
    name: field.name,
    type: mapProtoTypeToFormType(field),
    label: field.comment ?? field.name,
    required: field.required,
    repeated: field.repeated,
    enumValues: resolveEnum(field),
    nestedSchema: field.resolvedType?.fields
      ? buildFormSchema(root, field.resolvedType.fullName)
      : undefined,
  }));
}
```

#### **3.4 参数枚举选择**

```text
能力：proto enum 自动转 select
来源：
  - 一级：proto 文件本身的 enum 定义
  - 二级：configsdk 中的动态枚举（如 module_key 列表，从 sys_config_schema 拉取）
  - 三级：人工标注的字段元数据（assets/field_meta.json）

UI：
  - 单选：select
  - 多选（repeated enum）：multiple select
  - 显示：value + name + description（来自 proto 注释或人工标注）
  - 搜索：枚举值多时支持搜索
```

二级动态枚举处理：

```text
某些字段的"枚举"实际上来自数据库（如 module_key、lang_code）：
  - 新建一个 src/data/dynamicEnum.ts
  - 通过特殊协议（如 6001 AppConfigsReq）拉取动态枚举
  - 缓存 5 分钟
  - 字段元数据中标注 "dynamic_enum_source": "module_keys"
```

#### **3.5 traceId 日志检索**

```text
能力：通过 traceId 串联客户端请求 / 响应 / 服务端日志
核心：
  - 每次请求自动生成 traceId（uuid v4）写入 extend.traceId
  - 请求面板顶部显示当前 traceId（一键复制）
  - 历史面板按 traceId 分组（含状态码、耗时、请求/响应大小）
  - 提供"日志检索"页面：
    a. 输入 traceId
    b. 调用日志服务 API（/api/dev/logs?traceId=xxx）
    c. 时间线展示：客户端请求 → Gateway → 各 Servant → 响应
    d. 高亮 ERROR / WARN

依赖：
  - 后端必须提供 dev-only 日志检索 API（仅内网可达）
  - 该 API 同样走 Gateway 但仅 dev-tester 角色可访问
  - 若后端未就绪：本工具先支持本地历史检索，预留 API 接入
```

UI 草图：

```text
顶部状态栏：
  TraceID: 7f3a2b... [Copy] [搜索同 traceId 历史] [打开服务端日志]

历史面板按 traceId 分组：
  · 7f3a2b...  6001 AppConfigsReq    200 OK     245ms   3 entries
    └── 客户端请求 (16:30:12.123) [展开]
    └── 服务端日志 (16:30:12.150) [展开]
    └── 响应 (16:30:12.368)       [展开]
```

### **五、关键流程：发送一次 Hello 请求**

```text
1. 选择协议 2100/2101 HelloWorldRequest
   → 加载 proto/base/hello.proto（protobuf.js）
   → 解析 message HelloWorldRequest → schema
   → 自动渲染表单（含 lang_code 枚举）

2. 用户填表：
   name = "张三"
   lang_code = "zh-CN"（来自动态枚举）

3. 选择测试用户：
   "运营张三" → 自动 login → token 写入 extend

4. 系统自动填充：
   traceId = uuid()
   requestId = uuid()
   maxType=2100, minType=2101
   clientVersion 来自 Settings
   platform = "tester"

5. 点击"发送"：
   a. 用 protobuf.js encode HelloWorldRequest → bytes
   b. 包装 MessagePacket：
      { maxType, minType, extend, data: bytes }
   c. encode MessagePacket → bytes
   d. POST /api/hello with body bytes (Content-Type: application/x-protobuf)

6. 收到响应：
   a. decode MessagePacket
   b. decode HelloWorldResponse
   c. 展示 JSON（左）+ raw hex（右）+ 耗时 + traceId

7. 写入历史：
   IndexedDB 存：traceId / 协议 / 入参 / 响应 / 耗时 / 状态

8. 查 traceId 日志：
   切换到 trace 页面 → 查询服务端 dev API → 时间线展示
```
