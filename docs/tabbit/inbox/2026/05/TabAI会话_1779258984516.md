整体结构应改成：`Gateway` 只负责统一入口、MessagePacket envelope、路由、鉴权、审计、JSON payload 转换；`userServer / groupServer / topicServer / authServer` 是独立业务模块，彼此不直接依赖；跨模块关联数据统一通过 `readonly` 只读模块读取；所有模块共同依赖 `common-lib` 工具模块。HelloWorld 和 HealthCheck 应作为第一个最小模块样板，按这个结构重构，并补齐单元测试、注释、集成测试、测试登记和文档。

### **一、先统一术语：local 是直连模式，不等于没有网关**

你这个理解是对的。建议后续统一使用下面这套术语：

```text
local 模式 = 单体部署直连模式
microservice / tars 模式 = 微服务远程调用模式
```

local 不是绕过 Gateway，也不是临时 mock。local 的含义应该是：

```text
客户端仍然只访问 Gateway。
Gateway 仍然解析 MessagePacket。

区别只是 Gateway 通过进程内 LocalInvoker 直接调用业务模块。
```

也就是说：

```text
local 模式：
Client → Gateway → LocalInvoker → users/auth/groups/topics 模块

microservice 模式：
Client → Gateway → TarsGoInvoker/RPCInvoker → userServer/authServer/groupServer/topicServer
```

两者的业务契约必须一致：

```text
同一个 maxType:minType
同一个 Protobuf message 定义
同一个 JSON payload 结构
同一个错误码语义
```

### **二、整体架构建议**

建议把架构明确成四层。

```text
Client / App / Admin Web / Open API
        ↓
Gateway 单网关层
        ↓
Invoker 调用适配层
        ↓
Business Modules / Servers
        ↓
Common Lib + Readonly Modules
```

更具体地说：

```text
Gateway
  ├── MessagePacket envelope 解析
  ├── maxType:minType 路由
  ├── MessagePacket.data JSON 编解码
  ├── 鉴权 / 审计 / trace / 错误包装
  └── Invoker 选择：local / tars / future-rpc

Invoker
  ├── LocalInvoker：单体部署直连业务模块
  └── TarsGoInvoker：微服务部署远程调用业务服务

Business Servers / Modules
  ├── userServer
  ├── authServer
  ├── groupServer
  ├── topicServer
  ├── helloServer
  └── healthServer

Readonly Modules
  ├── userReadonly
  ├── groupReadonly
  ├── topicReadonly
  └── authReadonly

Common Lib
  ├── errors
  ├── result
  ├── json codec
  ├── context / trace
  ├── validation
  ├── time / id
  └── test helpers
```

核心规则是：

```text
业务 Server 之间不直接相互调用。
跨模块读取关联数据，只通过 readonly 只读模块。
所有模块可以共同依赖 common-lib。
common-lib 不反向依赖任何业务模块。
readonly 可以依赖数据访问层或查询接口，但不写业务状态。
```

### **三、模块依赖规则**

这部分必须写成硬规则，否则后续会乱。

#### **允许依赖**

```text
Gateway → Invoker
```

```text

topicServer 基于快照执行业务判断。
```

例如 group 需要知道 user 信息：

```text

groupServer 调用 userReadonly.GetUserSnapshot(userId)。
```

这样可以避免模块之间循环依赖，也方便后续拆成微服务。

### **五、MessagePacket.data 的最终口径**

结合你前面的说明，建议写成：

```text
MessagePacket 是 Gateway envelope。
MessagePacket.data 承载 JSON payload。
JSON payload 的字段语义由 Protobuf message 定义。
业务模块接收 Protobuf message 对齐的对象或 JSON DTO。
业务模块不接收 MessagePacket。
```

所以处理链路是：

```text
HTTP JSON / MessagePacket
        ↓
Gateway 解析 maxType:minType
        ↓
Gateway 根据 routes 找到 request/response message
        ↓
Gateway 解码 MessagePacket.data JSON
        ↓
转换为模块请求对象 / JSON DTO
        ↓
LocalInvoker 或 TarsGoInvoker 调用模块
        ↓
模块返回响应对象 / JSON DTO
        ↓
Gateway 编码为 MessagePacket.data JSON
        ↓
返回客户端
```

这里必须特别提醒 Trae：

```text
不要让 users/auth/groups/topics 模块直接 import gateway/internal/messagepacket。
不要让模块测试通过构造 MessagePacket 才能运行。
模块单测应该直接测试模块 request/response。
```
