#### **🟡 收紧 2：§3.3 protoFormBuilder 通过"constructor 参数形状推导字段列表"不可行**

```text
事实：v1.1 §3.3 T1.3 写：
  "通过 reqMessageClass 字符串动态 import google-protobuf 生成类
   分析类的 constructor 参数形状推导字段列表"

问题：
  - google-protobuf 生成的 TS 类构造器签名是 constructor(opt_data?: Message.MessageArray)
    完全没有字段形状信息可"反射"
  - 字段定义藏在生成代码的 .getXxx() / .setXxx() 方法里，靠扫方法名是不稳的
  - protoc-gen-ts 不同版本生成的方法命名规则不一致（有的带 List 后缀，有的不带）

后果：
  - 按 v1.1 描述实现 → 跑不通
  - 跑通需要额外解析 .proto 文件 → 等于又走回运行时反射老路
```

**裁决：**

```text
✅ 改为"完全由 gen-protocols.mjs 在构建期解析 .proto 输出字段元数据"

修订要点：
  1. 字段列表的唯一来源 = protocols.json.fields[]
     （不再依赖运行时反射生成类）
  
  2. 字段元数据扩展（在 ProtocolMeta 之外新增 messageSchemas）：
     protocols.json {
       "protocols": [...],          // 12 条协议
       "messageSchemas": {           // 新增：所有引用到的 message 字段元数据
         "HelloWorldRequest": {
           "fields": [
             {
               "name": "name",
               "fieldNumber": 1,
               "type": "string",
               "repeated": false,
               "oneofGroup": null,
               "required": false,
               "comment": "问候名称",
               "defaultValue": ""
             },
             ...
           ]
         },
         "AppConfigsReq": {...},
         "DynamicConfigModule": {...},
         ...
       }
     }
  
  3. gen-protocols.mjs 用 protobufjs 的 parse 函数（不是 load）做纯静态解析
     parse 函数只做语法分析，输出 AST 后转 messageSchemas
     这是构建期能力，不进运行时（运行时仍只有 google-protobuf）
     
  4. protoFormBuilder 重写：
     输入：protocolMeta + messageSchemas（来自 protocols.json）
     输出：FormFieldSchema[]
     运行时不 import .proto，不做反射
  
  5. 类型映射（field.type → FormFieldType）由 gen-protocols.mjs 静态完成
     - TYPE_STRING → "string"
     - TYPE_INT32 / TYPE_INT64 / TYPE_UINT32 → "number"
     - TYPE_BOOL → "boolean"
     - TYPE_BYTES → "bytes"
     - TYPE_ENUM → "enum"（含枚举值列表）
     - TYPE_MESSAGE → "message"（含 nestedSchema 引用名）
     - repeated → "repeated" 包装
     - map<K,V> → "map" 包装

明确禁止：
  ❌ 禁止在 protoFormBuilder 运行时 import .proto 文件
  ❌ 禁止用 google-protobuf 生成类的 .toObject() 推断字段（顺序不稳）
  ❌ 禁止用 keysOf(class.prototype) 扫方法名推断字段（命名规则不稳）
```

#### **🟡 收紧 3：§3.6 + T4.3 token 持久化策略自相矛盾**

```text
事实：
  §3.6 写："Token 仅存内存 + localStorage hash（不上送任何外部）"
  T4.3 写："严格不持久化 fullToken（仅 hash 摘要存 localStorage, key: pt:token:hash）"
  §1.2 铁律写："不持久化 Token"

问题：
  - 三处描述的"hash 摘要"用途不明：
    a. 用于刷新后识别"上次是哪个用户"？→ 但用户切换面板能解决
    b. 用于安全审计？→ 但 hash 后无法反查
    c. 还是其实是"前几位明文 + 后几位省略"的 display label？
  - 真正"hash"无法用于发请求，刷新页面后 token 仍然丢失，hash 没意义
```

**裁决：**

```text
✅ 完全删除"localStorage hash"概念，token 100% 内存化

修订要点：
  1. §3.6 "Token 仅存内存 + localStorage hash" → 改为 "Token 仅存内存（sessionStorage 或 Zustand session store）"
  
  2. T4.3 删除"hash 摘要存 localStorage"分支
  
  3. 刷新页面后行为：
     - 当前用户 ID 保留在 localStorage（非敏感）
     - 重新渲染时显示"用户：运营张三 [需重新装载 Token]"
     - 用户点一次"装载"按钮 → 从 test_users.json fixedToken 重新写入内存
     - 5 秒不点 → 显示警示横幅
  
  4. UI 上保留"复制当前 token hash 用于审计"按钮（仅显示用，不持久化）
     - hash 计算在前端纯计算，仅供显示
     - 不存 localStorage
  
  5. test_users.json 中的 fixedToken 本身是 dev-only 数据，已经在源码里
     不需要再用 localStorage 复制一份

理由：
  - 既然 fixedToken 在 test_users.json 中能拿到，localStorage 完全冗余
  - 任何形式的 token 持久化都是攻击面（同源 XSS / 浏览器扩展读取）
  - "刷新需重新装载"对内部工具不是负担，反而是安全增强
```

#### **🟡 拍板 1：CSP header 具体配置值**

```text
v1.1 §T4.4 只写"CSP header 配置（nginx 或 meta tag）"，没给具体值。
T-1 实施时如果开发自己写一个，大概率写得过松或过紧。
```

**裁决（主控直接拍板）：**

```text
✅ 给出 CSP 字符串硬编码，写入 index.html <meta>，T0.5 README 同步说明

<meta http-equiv="Content-Security-Policy" content="
  default-src 'self';
  script-src 'self' 'unsafe-inline';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data:;
  connect-src 'self' http://localhost:8080 http://127.0.0.1:8080;
  font-src 'self' data:;
  object-src 'none';
  base-uri 'self';
  form-action 'none';
  frame-ancestors 'none';
">

关键约束说明：
  - connect-src 仅允许 localhost:8080 + 127.0.0.1:8080
    确保 Token 永不发送到任何非 Gateway 域名
  - object-src 'none' + frame-ancestors 'none'
    防止页面被嵌入 iframe 或加载插件
  - form-action 'none'
    proto-tester 全部走 fetch，不应有 form 提交
  - script-src 不允许 unsafe-eval
    防止 JSON.parse 之外的代码执行
  - style-src 'unsafe-inline' 保留
    Ant Design 5 + CodeMirror 6 都有 inline style，移除会导致样式崩溃

切换 endpoint 时：
  - Settings 页面修改 endpoints.json 中 baseUrl
  - 修改后必须刷新页面（让 CSP meta 重新生效）
  - 或在 vite dev 模式下读取 .env.local 注入 connect-src 列表
```
