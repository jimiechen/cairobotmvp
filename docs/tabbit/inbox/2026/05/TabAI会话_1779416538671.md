### **服务端代码层面通过统一的 ConfigClient / I18nClient SDK 快速引用，admin-server 仅承担后台运维 UI，绝不进入业务读路径，OpenAPI 与所有业务服务统一从 services/config + services/i18n 取数。**

下面这版方案在前两轮基础上补齐两个关键缺口：

```text
缺口 1：业务服务（OpenAPI、设备网关、用户中台、AI 服务）如何在代码层面
        快速、统一、热更地引用全局配置与多语言。
缺口 2：明确 admin-server 的边界 —— 它只是运维 UI 的后端，不在业务请求链路上。
```

### **一、架构边界重新明确**

#### **1.1 三类调用方与三条数据流**

```text
┌─────────────────────────────────────────────────────────────┐
│                   写路径（运维侧，低频）                      │
│  admin-web (Vue/React)                                       │
│        │ HTTP                                                │
│        ▼                                                     │
│  admin-server (Go/Gin)                                       │
│        │ 直接读写 MySQL                                      │
│        ▼                                                     │
│  sys_config_schema / sys_config_version                      │
│  sys_lang_pack / sys_lang_string                             │
│        │ 同时主动失效 Redis 缓存                             │
│        ▼                                                     │
│  Redis (config:* / i18n:*)                                   │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│                客户端读路径（高频，走网关）                   │
│  App / Web / 第三方                                          │
│        │ POST /api/hello + MessagePacket                     │
│        ▼                                                     │
│  proto-gateway                                               │
│        │ TarsGo bytes                                        │
│        ▼                                                     │
│  tars/config / tars/i18n Servant                             │
│        │ 调用                                                │
│        ▼                                                     │
│  services/config / services/i18n                             │
│        │                                                     │
│        ▼                                                     │
│  Redis → MySQL                                               │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│            服务端业务读路径（本次新增重点）                  │
│  OpenAPI / 设备网关 / 用户中台 / AI 服务 / Gateway 自身       │
│        │ Go 函数调用（同进程或跨进程）                       │
│        ▼                                                     │
│  configsdk.Client / i18nsdk.Client                           │
│        │ 内存 LRU + 后台订阅                                 │
│        ▼                                                     │
│  Redis (热路径) → services/config（冷路径）                  │
└─────────────────────────────────────────────────────────────┘
```

三条流的关键约束：

```text
- admin-server 只在写路径，不在业务读路径。
- OpenAPI 等业务服务读取配置 / 多语言时，绝不调用 admin-server。
- 所有读路径最终都会汇聚到 services/config / services/i18n。
- admin-server 与业务服务通过 Redis pub/sub 协作做缓存失效，不直接互调 API。
```

#### **1.2 为什么 OpenAPI 不能调用 admin-server**

```text
1. admin-server 部署在内网管理段，对外不可达。
2. admin-server 没有按业务请求量级做容量规划。
3. admin-server 的鉴权体系是运维账号体系，与业务鉴权不兼容。
4. 一旦业务依赖 admin-server，运维发版会直接导致业务抖动。
5. 旧项目的事故根因之一就是 admin / 业务读路径混淆。
```

业务读路径必须只走 services/config + services/i18n。admin-server 仅是 schema/value/string 的运营 UI 后端。

### **二、统一 SDK：configsdk / i18nsdk**

把"服务端代码层面快速引用"具象化为两个 SDK 包，所有业务服务只引这两个包。

#### **2.1 包位置**

```text
go/services/config/sdk/   ← configsdk
go/services/i18n/sdk/     ← i18nsdk
```

放在 services/* 下而不是 third_party/，因为它们是业务领域 SDK，不是基础设施。所有业务服务通过 go.work 引用。

#### **2.2 configsdk 对外 API（最小完整集）**

```go
package configsdk

// 客户端句柄，进程内单例
type Client interface {
    // 强类型读取（编译期可知字段名）
    GetString(ctx context.Context, moduleKey, fieldKey string) (string, error)
    GetInt(ctx context.Context, moduleKey, fieldKey string) (int64, error)
    GetBool(ctx context.Context, moduleKey, fieldKey string) (bool, error)
    GetFloat(ctx context.Context, moduleKey, fieldKey string) (float64, error)
    GetJSON(ctx context.Context, moduleKey, fieldKey string, out any) error

    // 整模块读取（适合一次拿一组）
    GetModule(ctx context.Context, moduleKey string) (Module, error)

    // 绑定到结构体（标签驱动）
    Bind(ctx context.Context, moduleKey string, out any) error

    // 监听变更（业务侧热更新）
    Watch(moduleKey string, handler func(Module)) (cancel func())

    // 健康检查
    Ping(ctx context.Context) error
}

type Module struct {
    Key       string
    Version   int64
    Fields    map[string]TypedValue
    UpdatedAt time.Time
}

type TypedValue struct {
    Type  string // string/int/bool/float/json/list
    Value any
}
```

业务方典型调用：

```go
cfg := configsdk.Default()  // 进程内单例
host, _ := cfg.GetString(ctx, "base_cfg", "domain_root")

// 或绑定结构体
type PayCfg struct {
    Methods []string `cfg:"methods"`
    MinAmt  float64  `cfg:"min_amount"`
}
var pc PayCfg
_ = cfg.Bind(ctx, "pay_cfg", &pc)

// 热更新订阅
cancel := cfg.Watch("member_cfg", func(m configsdk.Module) {
    log.Printf("member_cfg updated: v=%d", m.Version)
})
```

#### **2.3 i18nsdk 对外 API**

```go
package i18nsdk

type Client interface {
    // 翻译 + 参数填充（服务端侧渲染场景，如短信、邮件、推送）
    T(ctx context.Context, langCode, key string, params map[string]any) (string, error)

    // 仅取原始模板（客户端渲染场景，如 Webhook 透传）
    Raw(ctx context.Context, langCode, key string) (Template, error)

    // 批量
    BatchT(ctx context.Context, langCode string, keys []string, params map[string]any) (map[string]string, error)

    // 监听语言包版本变化
    Watch(langCode string, handler func(packVersion int64)) (cancel func())

    Ping(ctx context.Context) error
}

type Template struct {
    Key          string
    Value        string
    TemplateType string  // plain / named / icu
    Params       []ParamSchema
}
```

服务端典型场景（必须服务端渲染的，如短信下发）：

```go
i18n := i18nsdk.Default()
text, _ := i18n.T(ctx, "zh-CN", "svc_msg_welcome", map[string]any{
    "name":  "张三",
    "count": 3,
})
// → "欢迎 张三，你有 3 条新消息"
```

注意：**客户端能渲染的优先客户端渲染**，服务端 `T()` 只用于推送/短信/邮件/Webhook 等服务端必须出文本的场景。

#### **2.4 SDK 内部三层缓存**

```text
L1：进程内 LRU
    - 读热点 ≤1ms
    - 容量按 module 数 × env 数估算（默认 1024 项）
    - TTL：30 秒（短，便于快速感知变更）

L2：Redis
    - 跨进程一致
    - TTL：10 分钟（config）/ 1 小时（i18n pack）
    - Key 与客户端读路径共享同一命名空间

L3：services/config / services/i18n（冷路径）
    - 单体模式：直接函数调用
    - 微服务模式：通过 Tars client 远程调用
    - 永远是 L1/L2 miss 的兜底
```

#### **2.5 SDK 的两种部署形态**

SDK 在 monolith / microservice 两种部署下行为完全一致，差异只在初始化：

```go
// 单体模式：直接注入 service 实现
configsdk.Init(configsdk.Options{
    Mode:    configsdk.ModeInProcess,
    Service: configSvc,             // 同进程的 *config.Service
    Redis:   rdb,
    Logger:  log,
})

// 微服务模式：通过 Tars 远程调用
configsdk.Init(configsdk.Options{
    Mode:        configsdk.ModeRemote,
    TarsServant: "cairobot.config.AppConfigsObj",
    Redis:       rdb,
    Logger:      log,
})
```

**业务代码完全无感**，不需要 if 分支。

#### **2.6 热更新机制**

```text
admin-server 写入 MySQL 后：
   ├─ 主动失效 Redis 对应 Key
   └─ 发布 Redis pub/sub 消息：
       channel: cairobot.config.invalidate
       payload: {"module":"member_cfg","version":42,"env":"prod"}

业务服务的 SDK 后台 goroutine：
   ├─ 订阅 cairobot.config.invalidate
   ├─ 收到消息后清除 L1 LRU 中的对应 entry
   └─ 触发 Watch 回调
```

这种机制的好处：

```text
- 无需服务端轮询 6009 协议（6009 是给客户端用的）
- 失效延迟通常 <100ms
- admin-server 不直接调用业务服务，纯单向广播，无强依赖
```

i18n 同样机制：

```text
channel: cairobot.i18n.invalidate
payload: {"lang_code":"zh-CN","pack_version":4,"env":"prod"}
```

### **三、admin-server 的精确职责定义**

#### **3.1 admin-server 只做四件事**

```text
1. 提供 admin-web 的 REST API（schema/value/string CRUD）
2. 写入 MySQL（sys_config_schema / sys_config_version / sys_lang_*）
3. 主动失效 Redis 缓存
4. 发布 Redis pub/sub 失效消息
```

#### **3.2 admin-server 绝不做这五件事**

```text
1. 不提供任何业务读 API（不暴露 GetConfig / Translate）
2. 不被 OpenAPI / 设备网关 / 用户中台 / AI 服务调用
3. 不出现在客户端协议链路上
4. 不直接被 services/config / services/i18n 引用
5. 不部署在业务网络段，仅内网运维段可达
```

#### **3.3 admin-server 与业务服务的协作只走两条线**

```text
线 1：MySQL（数据共享）
   admin-server 写 → 业务服务 SDK 读
   通过 schema 与 version 字段保证一致性

线 2：Redis pub/sub（事件广播）
   admin-server 发 → 业务服务 SDK 订阅
   单向、无强依赖、可丢失（业务侧 SDK 还有 TTL 兜底）
```

#### **3.4 旧项目的反例**

旧项目把 admin-server 与业务读路径混在一起，最终导致：

```text
- pay_cfg 历史版本堆积（admin 写得太随意，业务读到旧版本）
- member_cfg 时间戳版本号（admin 写时没走 services 层校验）
- 双重存储漂移（admin 写两套，业务读不一致）
```

新方案通过 **"业务永不调用 admin-server"** 这一条铁律根治。

### **四、OpenAPI 与其他业务服务的标准接入姿势**

#### **4.1 OpenAPI 接入示例**

```go
// go/services/openapi/cmd/server/main.go
func main() {
    rdb := redisx.MustOpen(cfg.Redis)
    db  := mysqlx.MustOpen(cfg.MySQL)

    // 微服务模式：openapi 通过 Tars 远程调用 config/i18n
    configsdk.Init(configsdk.Options{
        Mode:        configsdk.ModeRemote,
        TarsServant: "cairobot.config.AppConfigsObj",
        Redis:       rdb,
        Logger:      log,
    })
    i18nsdk.Init(i18nsdk.Options{
        Mode:        i18nsdk.ModeRemote,
        TarsServant: "cairobot.i18n.AppConfigsObj",
        Redis:       rdb,
        Logger:      log,
    })

    // 业务服务正常启动
    openapi.Run(...)
}
```

OpenAPI 内部典型用法：

```go
func (h *DeviceHandler) WebhookURL(ctx context.Context, tenantID string) (string, error) {
    base, err := configsdk.Default().GetString(ctx, "base_cfg", "domain_root")
    if err != nil {
        return "", err
    }
    return base + "/api/v1/webhook/" + tenantID, nil
}

func (h *DeviceHandler) PushTitle(ctx context.Context, lang string) (string, error) {
    return i18nsdk.Default().T(ctx, lang, "svc_push_device_online", nil)
}
```

业务代码完全不感知 admin-server 是否存在。

#### **4.2 各业务服务统一接入清单**

```text
| 业务服务         | 部署模式      | SDK 模式  | 备注                            |
| OpenAPI          | microservice | Remote    | 公网入口，需 Redis 高可用       |
| 设备网关         | microservice | Remote    | 高频读，开 L1 LRU              |
| 用户中台         | monolith     | InProcess | 与 Gateway 同进程              |
| AI 服务 (Python) | microservice | -         | 用 Python SDK（见下节）         |
| Gateway 自身     | monolith     | InProcess | 用于 MessagePacket extend 默认值 |
```

#### **4.3 Python 侧 SDK（AI 服务）**

AI 服务是 Python，提供对等的 `cairobot-config-sdk-py`：

```text
- 通过 grpc 或 Tars Python client 调用 services/config / services/i18n
- 同样三层缓存：本地 LRU + Redis + 远程
- 同样订阅 Redis pub/sub 做失效
- 提供 ConfigClient / I18nClient 同名接口
```

实现细节本次不展开，但接口与 Go SDK 对等，避免两侧语义漂移。

### **五、配置 / 多语言 在服务端代码中的「快速增加」闭环**

把"快速增加"拆成 4 个动作，每个动作都有明确角色：

#### **5.1 快速增加配置字段**

```text
角色 A：运营在 admin-web 上：
   - 选定 module_key（如 member_cfg）
   - 新增 field_key（如 max_premium_plus_group）
   - 设置 type/default/validator/scope/min_app_ver
   - 保存

角色 B：admin-server：
   - 写入 sys_config_schema
   - 同步默认值到 sys_config_version
   - 失效 Redis：config:schema:* + config:value:member_cfg:*
   - 发布 pub/sub：cairobot.config.invalidate

角色 C：业务服务（OpenAPI 等）：
   - SDK 收到 pub/sub，清除 L1 LRU
   - 下次 GetInt(ctx, "member_cfg", "max_premium_plus_group") 自动返回新字段
   - Go 代码完全不动，无需重新编译/部署

角色 D：客户端：
   - 通过 6009 轮询发现版本变化
   - 拉 6001 拿到 dynamic_modules 中的新字段
   - 老客户端无视新字段，新客户端按需消费
```

整个链路无 Go 代码改动、无服务发布。

#### **5.2 快速增加多语言 key（带参数）**

```text
角色 A：运营在 admin-web 上：
   - 新增 string_key = svc_msg_low_balance
   - template_type = named
   - params_schema = [{name:"amount",type:"float",required:true}]
   - zh-CN: "余额不足，当前 {amount} 元"
   - en:    "Low balance: {amount} USD"
   - preview_sample = {"amount": 9.9}
   - 保存

角色 B：admin-server：
   - template_validator 强校验占位符与 params_schema 一致
   - 写入 sys_lang_string（每语言一行）
   - sys_lang_pack.version 自增
   - 失效 Redis：i18n:pack:* + i18n:diff:*
   - 发布 pub/sub：cairobot.i18n.invalidate

角色 C：业务服务（如支付服务发送短信）：
   - i18nsdk.Default().T(ctx, userLang, "svc_msg_low_balance",
                          map[string]any{"amount": 9.9})
   - 直接拿到渲染后字符串，发短信即可

角色 D：客户端：
   - 6007 增量拉到新 key 与 params 描述
   - UI 调用 t() 自行渲染
```

#### **5.3 关键质量门**

```text
质量门 1：admin-server 保存前 schema/template 强校验
   - 配置：field_key 命名规范、type 合法、validator 可解析
   - i18n：占位符与 params_schema 一致、各语言占位符集合一致、
           preview_sample 必须能成功渲染

质量门 2：services 层只接受 schema-合规 的数据
   - SDK 读到 schema 不识别的字段时降级到默认值，不抛异常
   - 配置 type 不匹配时记录 metric 并降级

质量门 3：客户端版本兼容
   - 服务端按 client_version 过滤 named/icu key
   - dynamic_modules 仅给新客户端识别
   - 老客户端永不会因新字段崩溃
```
