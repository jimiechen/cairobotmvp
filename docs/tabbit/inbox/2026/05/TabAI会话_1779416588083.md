### **基于现有 CODE-WIKI 分层骨架，新增"配置元模型 + 自描述注册表 + 多语言参数化模板"两套机制，让后台快速加配置、客户端拿到带参数填充的多语言文案，无需改 Go 代码与发布服务。**

下面这版方案完全对齐你当前 CaiRobot MVP 的 S0 骨架（单网关 + MessagePacket + routes.yaml + TarsGo bytes 接口 + 分层 modules），不再重新设计目录，而是聚焦在两个真正影响"快速迭代"的能力上：

```text
能力 1：快速增加配置
  → 后台动态新增 module_key + field_schema，服务端零代码上线
能力 2：快速增加多语言 key
  → 后台直接注册 key + 参数定义，客户端按 ICU/占位符规则填充
```

这两块正是旧项目最痛的地方：旧项目每加一个配置字段要改 proto + config_query.go + admin-server + admin-web 四处，每加一个多语言 key 要走完整发版。新方案要把"加配置"和"加多语言"变成 **后台运营动作**，不再是 **研发发布动作**。

### **一、问题定位与设计目标**

#### **1.1 当前架构能解决什么、不能解决什么**

```text
当前 services/config + services/i18n 分层已经解决：
  ✓ 单文件超限
  ✓ 双重存储
  ✓ 缓存硬编码
  ✓ 双部署模式

当前架构未解决：
  ✗ 新增配置字段仍需改 proto + Go 代码 + 重发服务
  ✗ 新增多语言 key 仍需改文案表 + 触发版本号 + 重发文案包
  ✗ 多语言文案缺少参数填充语义（如"欢迎 {name}，你有 {count} 条消息"）
  ✗ 后台运营无法在不打扰研发的情况下迭代
```

#### **1.2 设计目标（本次明确）**

```text
G1. 配置侧：后台新增字段无需改 Go 代码，最多改 admin-web 表单 schema。
G2. 配置侧：客户端通过统一协议拿到任意结构的配置，不依赖 proto 强类型。
G3. 多语言侧：后台新增 key 即时生效（增量协议立刻能拉到）。
G4. 多语言侧：支持参数化模板（命名占位符 + 复数 + 默认值）。
G5. 不破坏现有 6001/6003/6005/6007 协议的 wire 兼容。
G6. 不引入新进程、不改部署模式。
```

### **二、核心机制一：配置元模型（Config Schema Registry）**

#### **2.1 旧问题回顾**

旧项目 `app_base.proto` 把每个 `module_key` 的字段写死在 proto：

```protobuf
message AppBaseConfigs {
  string domain_root = 1;
  string domain_wap = 2;
  // ... 33 个字段
}
```

每加一个字段：proto 改一次、`config_query.go` 解析改一次、admin-server 填充改一次、admin-web 表单改一次。**任何一处遗漏都不会编译报错，只会运行时返回默认值**（旧项目 P-02 的根因）。

#### **2.2 新机制：自描述配置 + 元数据驱动**

把配置从"强类型 proto" 改造成 **"元数据 + 通用容器"**：

```text
sys_config_schema     ← 新增：定义某个 module_key 有哪些 field、类型、默认值
sys_config_version    ← 复用：存储某个 module_key 的当前 JSON 配置值
```

`sys_config_schema` 表结构：

```sql
CREATE TABLE sys_config_schema (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  module_key    VARCHAR(100) NOT NULL,
  field_key     VARCHAR(100) NOT NULL,
  field_type    VARCHAR(32)  NOT NULL,  -- string/int/bool/float/enum/json/list
  default_value TEXT,
  validator     VARCHAR(255),           -- 正则/范围/枚举值，JSON 表达
  is_required   TINYINT DEFAULT 0,
  is_secret     TINYINT DEFAULT 0,      -- 是否客户端可见
  description   VARCHAR(500),
  client_scope  VARCHAR(64),            -- all / android / ios / web / admin
  min_app_ver   VARCHAR(32),            -- 最低支持的客户端版本
  created_at    DATETIME,
  updated_at    DATETIME,
  UNIQUE KEY uk_module_field (module_key, field_key)
) ENGINE=InnoDB;
```

后台运营加字段流程：

```text
1. 在 admin-web 配置管理页填写 module_key + field_key + field_type + 默认值
2. admin-server 写入 sys_config_schema
3. 自动在 sys_config_version 下游同步默认值
4. 客户端通过 6001 立即拿到新字段，无需发版
```

研发完全不用动 Go 代码。

#### **2.3 协议层调整：通用容器替换强类型字段**

把 `AppConfigsRsp` 改成自描述结构，**保持 6001 协议号不变，仅扩展 message 字段**：

```protobuf
// proto/base/app_config.proto
message AppConfigsRsp {
  Result result = 1;

  // 旧字段保留（兼容旧客户端），但服务端按 schema 自动填充
  AppBaseConfigs    base_cfg   = 2;
  AppWapUrlConfigs  wap_cfg    = 3;
  AppRegexConfigs   regex_cfg  = 4;
  AppPayConfigs     pay_cfg    = 5;
  AppOssConfigs     oss_cfg    = 6;
  AppLanguageConfigs lang_cfg  = 7;
  AppMuteConfigs    mute_cfg   = 8;
  AppGroupConfigs   group_cfg  = 9;

  // 新增：自描述模块容器，新模块/新字段都走这里
  repeated DynamicConfigModule dynamic_modules = 100;
}

message DynamicConfigModule {
  string module_key = 1;
  int64  version    = 2;
  // 字段 → JSON-encoded value，类型由 schema 描述
  map<string, string> fields = 3;
  // 可选：内嵌 schema 摘要，便于调试
  repeated FieldDescriptor descriptors = 4;
}

message FieldDescriptor {
  string field_key   = 1;
  string field_type  = 2;  // string/int/bool/float/enum/json/list
  bool   is_required = 3;
  string default_val = 4;
}
```

这样：

```text
- 旧客户端：依赖 base_cfg/member_cfg 等强类型字段，行为不变
- 新客户端：读 dynamic_modules，可以处理任意新字段
- 服务端：用 schema 自动填充强类型字段，新字段只下发到 dynamic_modules
```

#### **2.4 services/config 内部改造**

不需要新增 module，只需在现有目录内加几个文件：

```text
go/services/config/
├── domain/
│   ├── module_key.go
│   ├── version.go
│   ├── schema.go          ← 新增：FieldSchema、ModuleSchema 实体
│   └── value.go           ← 新增：TypedValue（按 field_type 解码）
├── repository/
│   ├── repository.go
│   ├── mysql_repo.go
│   ├── sqlite_repo.go
│   └── schema_repo.go     ← 新增：sys_config_schema CRUD
├── cache/
│   └── ...                ← 不变
└── service/
    ├── service.go
    ├── fetch.go
    ├── parse.go           ← 改造：按 schema 而非硬编码解析
    ├── validate.go        ← 改造：按 schema.validator 校验
    ├── schema.go          ← 新增：SchemaService（运营接口）
    └── compose.go         ← 新增：合并强类型字段 + dynamic_modules
```

`compose.go` 是关键，它做一件事：

```text
输入：env、client_scope、client_version、用户 module_key 列表
输出：
  - 强类型字段（base_cfg / member_cfg / ...）：按 schema 默认值 + DB 实际值填充
  - dynamic_modules：DB 中存在但强类型 proto 没有的 module_key/field_key
```

新增字段的判断完全由 `sys_config_schema` 驱动，Go 代码零改动。

#### **2.5 admin 侧的对应能力**

```text
admin-web 新增页面：
  /admin/config/schema       ← 字段元数据管理
  /admin/config/value         ← 字段值管理（按 schema 动态渲染表单）

admin-server 新增 API：
  POST   /api/config/schema       新增字段定义
  PUT    /api/config/schema/:id   修改字段定义
  DELETE /api/config/schema/:id   软删除字段
  GET    /api/config/schema       列表
  GET    /api/config/value/:env   按 env 获取所有 module_key 值
  PUT    /api/config/value        更新某 module_key 的值
```

**研发只需要在 schema 系统稳定后，几乎不再介入新增配置字段的过程**。

#### **2.6 缓存策略变化**

新增缓存 Key：

```text
config:schema:{module_key}                 TTL = 5 分钟
config:schema:all                          TTL = 5 分钟（全量）
config:value:{env}:{module_key}:{version}  TTL = 10 分钟（已有）
config:compose:{env}:{client_scope}:{ver_hash}  TTL = 10 分钟（合成结果）
```

`ver_hash` 由所有 module_key 当前 version + schema version 拼成 fnv64 哈希，schema 变更立刻让缓存失效。

### **三、核心机制二：多语言参数化模板**

#### **3.1 旧问题回顾**

旧项目 `sys_lang_string`：

```text
string_key = "svc_app_welcome"
string_value = "欢迎使用"
```

**纯静态文本**，无法支持：

```text
- "欢迎 {name}"
- "你有 1 条消息" / "你有 5 条消息"（复数）
- "{date, date, short} 注册"（格式化）
```

每次需要参数化都靠客户端各端各自拼字符串，行为不一致、维护成本高。

#### **3.2 新机制：ICU MessageFormat 子集**

在 `sys_lang_string.string_value` 中支持 **命名占位符 + 复数 + select**，并在 `sys_lang_string` 增加参数描述字段。

`sys_lang_string` 表扩展（不破坏既有数据）：

```sql
ALTER TABLE sys_lang_string
  ADD COLUMN template_type VARCHAR(16) DEFAULT 'plain'
    COMMENT 'plain/named/icu',
  ADD COLUMN params_schema JSON DEFAULT NULL
    COMMENT '参数描述：[{name,type,required,default}]',
  ADD COLUMN preview_sample JSON DEFAULT NULL
    COMMENT '预览示例值，便于后台预览渲染';
```

#### **3.3 三种模板类型**

```text
template_type = plain
  示例: "欢迎使用"
  渲染: 原样返回

template_type = named
  示例: "欢迎 {name}，你有 {count} 条新消息"
  params_schema:
    [
      {"name":"name","type":"string","required":true},
      {"name":"count","type":"int","required":true}
    ]
  渲染: 客户端按 {name} 替换

template_type = icu
  示例:
    "{count, plural,
       =0 {你没有新消息}
       one {你有 # 条新消息}
       other {你有 # 条新消息}
     }"
  params_schema:
    [{"name":"count","type":"int","required":true}]
  渲染: 客户端用 ICU runtime（如 messageformat-go / Flutter intl / iOS NSLocalizedString）
```

ICU 是国际通行规范，Flutter / Android / iOS / Web 都有现成 runtime，不需要自己造轮子。

#### **3.4 协议层扩展**

`AppFetchLangPackRsp` / `AppFetchLangDifferenceRsp` 中每个 string 由原来的 `(key, value)` 升级为 `(key, value, type, params)`，**保留旧字段做兼容**：

```protobuf
message LangStringEntry {
  string key   = 1;
  string value = 2;                       // 旧客户端只读这个，按 plain 处理
  string template_type = 3;               // 新增：plain/named/icu
  repeated LangParam params = 4;          // 新增：参数描述
  string operation_type = 5;              // ADD/MOD/DEL（增量协议用）
}

message LangParam {
  string name      = 1;
  string type      = 2;  // string/int/float/date
  bool   required  = 3;
  string default_v = 4;
}
```

旧客户端拿到 `value="欢迎 {name}"` 会原样显示（包含花括号），但这种 key 默认只下发给 `min_app_ver` 满足条件的客户端，避免兼容问题。

#### **3.5 后台快速新增多语言 key 的流程**

```text
1. 运营在 /admin/i18n/string 页面新增：
   - key: svc_msg_welcome
   - template_type: named
   - params_schema: [{name,string,required},{count,int,required}]
   - 各语言 value:
       zh-CN: "欢迎 {name}，你有 {count} 条新消息"
       en:    "Welcome {name}, you have {count} new messages"
   - preview_sample: {"name":"张三","count":3}

2. 后台保存 → admin-server:
   - 写入 sys_lang_string（每语言一行，operation_type=ADD）
   - sys_lang_pack.version 自增 1
   - 失效 i18n 相关缓存

3. 客户端：
   - 通过 6009 协议轮询发现 sys_lang_pack.version 变化
   - 调用 6007 拉增量，拿到新 key
   - UI 调用 t("svc_msg_welcome", {name:"张三", count:3}) 渲染

整个过程零研发介入。
```

#### **3.6 services/i18n 内部改造**

```text
go/services/i18n/
├── domain/
│   ├── lang_pack.go
│   ├── lang_string.go     ← 增加 TemplateType / ParamsSchema 字段
│   ├── operation.go
│   ├── version.go
│   └── template.go        ← 新增：模板类型枚举与校验规则
├── repository/...           ← 增加 ParamsSchema JSON 读写
├── cache/...                ← 不变
└── service/
    ├── service.go
    ├── pack.go
    ├── diff.go
    ├── language.go
    ├── publish.go
    ├── template_validator.go ← 新增：保存前校验占位符与 params_schema 一致性
    └── compat_filter.go      ← 新增：按 client_version 过滤 named/icu key
```

`template_validator.go` 是质量门，运营保存时强校验：

```text
- value 中所有 {xxx} 占位符必须出现在 params_schema 中
- params_schema 中所有 required=true 的参数必须出现在 value 中
- 中英文 value 的占位符集合必须一致（避免某语言漏参数导致客户端崩溃）
- preview_sample 必须能成功渲染
```

服务端不做模板渲染，**渲染由客户端完成**，避免服务端承担多语言运行时。

#### **3.7 兼容期下发策略**

```text
旧客户端（无 template_type 字段感知能力）：
  → 服务端只下发 template_type=plain 的 key，过滤掉 named/icu

新客户端：
  → 全量下发，由客户端运行时按 template_type 选择渲染分支
```

通过协议中的 `client_version` 透传字段（已在 MessagePacket.extend 中标准化）做过滤。
