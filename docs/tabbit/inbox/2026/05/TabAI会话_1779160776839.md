# 二、运行模式要求

## 2.1 单体模式 Monolith Mode

单体模式用于：

- 本地开发
- 单元测试
- CI 最小链路测试
- 没有 TarsCloud 环境时的演示

单体模式下：

```text
POST /api/hello
        ↓
Gateway
        ↓
routes.yaml
        ↓
Local/InProcess Invoker
        ↓
本地业务模块 handler
        ↓
返回 response bytes
```

特点：

- 不依赖真实 TarsCloud。
- 不启动多个服务进程。
- Gateway 与业务模块可以在同一进程内运行。
- 使用统一 bytes 方法签名。
- 仍然严格走 routes.yaml。
- 仍然以 `maxType/minType` 为主路由键。
- 仍然返回 MessagePacket。
- 不能绕过 Router。
- 不能因为单体模式就直接调用业务函数绕过统一协议。

建议单体模式 Invoker：

```go
type LocalInvoker struct {
    handlers map[string]LocalHandler
}

type LocalHandler interface {
    Invoke(ctx context.Context, request []byte, extend map[string]string) (int, []byte, error)
}
```

handler key 可以使用：

```text
tars_app.tars_server.tars_servant.tars_method
```

例如：

```text
CaiRobot.SystemServer.SystemObj.HealthCheck
```

单体模式也必须保持 Tars 统一签名语义：

```go
Invoke(ctx, requestBytes, extend) -> returnCode, responseBytes, error
```

## 2.2 微服务模式 Microservice Mode

微服务模式用于：

- dev / test / staging / prod 环境
- 真实 TarsCloud 部署
- 多服务独立扩缩容
- 服务治理和灰度发布

微服务模式下：

```text
POST /api/hello
        ↓
Gateway
        ↓
routes.yaml
        ↓
TarsGoInvoker
        ↓
TarsCloud
        ↓
CaiRobot.XxxServer.XxxObj.Method
        ↓
返回 response bytes
```

特点：

- 每个业务模块作为独立 TarsGo Server 运行。
- Gateway 通过 TarsCloud/TarsGo client 调用。
- 每个服务独立构建、独立测试、独立部署。
- Gateway 不能直接 import 业务模块 internal 包。
- TarsCloud App/Server/Servant 按 `docs/api/tars规范.md`。
- Tars 方法签名统一为：

```tars
int Xxx(vector<byte> request, map<string,string> extend, out vector<byte> response);
```

如果当前阶段尚未接入真实 TarsGo client，可以先保留：

```go
type TarsGoInvoker struct {
    // TODO: integrate real TarsGo client
}
```

并确保 Gateway 通过配置选择 local 或 tars 模式。

# 七、实现建议

## 7.1 Gateway Invoker 抽象

建议在 Gateway 中定义：

```go
package tarsclient

import "context"

type Target struct {
    App       string
    Server    string
    Servant   string
    Module    string
    Interface string
    Method    string
}

type Invoker interface {
    Invoke(ctx context.Context, target Target, request []byte, extend map[string]string) (int, []byte, error)
}
```

LocalInvoker：

```go
type LocalHandler interface {
    Invoke(ctx context.Context, request []byte, extend map[string]string) (int, []byte, error)
}

type LocalInvoker struct {
    handlers map[string]LocalHandler
}
```

目标 key：

```go
func TargetKey(t Target) string {
    return t.App + "." + t.Server + "." + t.Servant + "." + t.Method
}
```

TarsGoInvoker：

```go
type TarsGoInvoker struct {
    // TODO: real TarsGo client
}
```

如果未实现：

```go
func (i *TarsGoInvoker) Invoke(...) (int, []byte, error) {
    return 10500, nil, errors.New("tars invoker is not implemented yet")
}
```

Gateway 启动时如果 mode=tars 且未实现，直接返回启动错误。

## 7.2 单体模式 handler 注册

建议在 Gateway 启动 local 模式时注册 System handler：

```go
localInvoker.Register(
    "CaiRobot.SystemServer.SystemObj.HealthCheck",
    systemhandler.NewHealthCheckHandler(),
)

localInvoker.Register(
    "CaiRobot.SystemServer.SystemObj.HelloWorld",
    systemhandler.NewHelloWorldHandler(),
)
```

但因为 Gateway 不能 import `tars/go/system/internal/...`，需要选择一种方式：

### 方案 A：system 模块提供非 internal 的 localhandler 包

例如：

```text
tars/go/system/localhandler
```

Gateway 可以 import：

```go
systemhandler "github.com/jimiechen/cairobotmvp/tars/go/system/localhandler"
```

该包只暴露 bytes handler，不暴露业务内部实现。

### 方案 B：Gateway 内置 minimal system local handler

当前阶段 Gateway 内部实现一个 minimal local system handler，仅用于本地链路验证。

优点：简单，不跨模块依赖。  
缺点：System 模块独立性弱一点。

### 推荐选择

本次建议采用 **方案 A**，因为你的要求是“业务模块独立存在，独立测试，通过 go work”。  
即：

```text
tars/go/system/localhandler
```

暴露：

```go
type Handler struct {}

func (h *Handler) Invoke(ctx context.Context, request []byte, extend map[string]string) (int, []byte, error)
```

Gateway local 模式通过 go work 引用 system/localhandler。

注意：

- `localhandler` 是该模块允许外部调用的适配层。
- 业务实现仍在 `internal/service`。
- Gateway 不 import `internal/service`。
