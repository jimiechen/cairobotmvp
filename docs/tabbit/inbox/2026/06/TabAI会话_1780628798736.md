### **一、针对问题 1：Content-Type 与请求体编码必须前置为 P0 门禁**

这是最重要的修订点。Gateway 实际强制要求：

```http
Content-Type: application/octet-stream
```

请求体不是 JSON，而是 `MessagePacket` 的 Protobuf 二进制 body。也就是说，任何使用：

```http
Content-Type: application/json
```

或者直接发送 JSON body 的 E2E 请求，都会被 Gateway 在入口层直接返回：

```http
415 Unsupported Media Type
```

因此，所有用例、CLI 执行、raw request 模板、proto-tester 编码验证都必须围绕这个事实重新修正。

#### **新增阶段 0 预检项：Gateway Content-Type 与 Body 编码确认**

把下面内容加入 `E2E-PREFLIGHT.md` 的必检项：

```text
新增 P0 预检：Gateway Content-Type 与请求体编码方式

请读取并记录 Gateway HTTP Server 的真实入口逻辑，重点确认：

1. Gateway 接受的 Content-Type：
   - 必须确认是否强制等于 application/octet-stream
   - 如果不是该值，实际返回什么 HTTP 状态码
   - 记录对应代码文件、函数名和行号

2. Gateway 请求体格式：
   - 是否读取 request body 为原始 bytes
   - 是否使用 proto.Unmarshal 解码 MessagePacket
   - MessagePacket 的 proto 定义路径
   - MessagePacket.data 字段的类型
   - data 字段内部是否再次承载业务 protobuf message bytes

3. proto-tester 当前发送行为：
   - CLI send.ts 如何构造 HTTP 请求 body
   - 是否对 MessagePacket 执行 protobuf 序列化
   - data 字段内部是业务 protobuf bytes，还是 JSON.stringify(payload) 的 UTF-8 bytes
   - headers 是否设置 Content-Type: application/octet-stream
   - 如果当前 proto-tester 发送行为与 Gateway 期望不一致，标记为 P0 FAIL/BLOCKED，并给出修复建议

4. 输出结论：
   - content_type_required: application/octet-stream
   - body_encoding: protobuf binary MessagePacket
   - business_payload_encoding: protobuf-message-bytes 或 json-string-utf8-bytes，以实际代码为准
   - proto_tester_encoding_compatible: true/false
```

#### **如果 proto-tester 当前确实是 JSON.stringify → UTF-8 bytes 的修复建议**

Trae 需要在报告中明确判断这是“设计兼容”还是“缺陷”。如果 Gateway/TarsGo 期望业务 data 是 protobuf message bytes，那么 proto-tester 需要修复：

```text
如果 proto-tester 当前把 payload JSON.stringify 后放入 MessagePacket.data，而 Gateway 下游期望 protobuf business message bytes，请标记为 P0 缺陷，并建议修复：

1. proto-tester 根据 protocols.json 找到 request_proto。
2. 使用对应 protobuf message schema 构造业务 request message。
3. 将业务 request message 序列化为 protobuf bytes。
4. 将该 bytes 写入 MessagePacket.data。
5. 再将整个 MessagePacket 序列化为 protobuf binary。
6. HTTP Header 设置 Content-Type: application/octet-stream。
7. capture 时同时保存：
   - raw HTTP body base64
   - decoded MessagePacket
   - raw MessagePacket.data base64
   - decoded business payload
```

### **三、针对问题 3：修正 routes.yaml 加载机制描述**

原方案中“Gateway 实际加载哪一份 routes.yaml”和“Gateway 内嵌副本”的措辞容易误导。根据新反馈，实际机制应该修正为：

```text
Gateway 通过 os.ReadFile(path) 从文件系统读取 routes.yaml。
默认路径是 configs/gateway/routes.yaml。
可通过 GATEWAY_ROUTES_PATH 环境变量覆盖。
go/gateway/proto-gateway/configs/gateway/routes.yaml 是开发/测试便利副本，不是 Go embed 内嵌配置。
```

因此，验收方案不应再暗示运行时会在“两份 routes.yaml”之间自动选择。真正的风险是：

```text
多份 routes.yaml 副本可能导致开发、测试、CI/CD 或手动启动时路径混淆。
```

#### **阶段 0 预检措辞修订**

把原来的：

```text
确认 Gateway 实际加载哪一份 routes.yaml
```

改成：

```text
确认 Gateway 默认 routes.yaml 加载路径、环境变量覆盖机制，以及多份 routes.yaml 副本是否会导致开发/测试/CI/CD 混淆。
```

#### **E2E-PREFLIGHT.md 必须记录的字段**

```yaml
gatewayRoutesLoading:
  mechanism: os.ReadFile(path)
  defaultPath: configs/gateway/routes.yaml
  overrideEnv: GATEWAY_ROUTES_PATH
  runtimeSource: filesystem
  goEmbed: false
  developmentCopy: go/gateway/proto-gateway/configs/gateway/routes.yaml
  developmentCopyUsage: 仅作为开发/测试便利副本，除非 GATEWAY_ROUTES_PATH 指向它，否则不应作为运行时配置来源
  risk: 多份 routes.yaml 副本内容不一致可能导致本地测试、CI、开发启动脚本使用不同路由表
```

#### **routes.yaml 一致性检查标题修订**

原标题：

```text

```

建议改为：

