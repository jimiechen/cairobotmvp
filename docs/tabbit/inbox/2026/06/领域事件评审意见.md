## 四、建议修改项（P1）

### 4.1 `DomainEvent.Payload` 类型选择值得商榷

方案 §6.1 定义 `Payload` 为 `map[string]interface{}`：

```go
Payload map[string]interface{} `json:"payload,omitempty"`
```

同时在 §9 的 `NewDomainEvent` 中也使用 `map[string]interface{}`。

**问题**：
- `map[string]interface{}` 失去了编译期类型检查
- 后续反序列化（如 Outbox 写入 JSON 再读出）时需要断言，容易出错
- 测试中断言 payload 字段也需要类型断言

**建议**：考虑使用 `json.RawMessage` 或定义 `any` 别名，并在 `payload.go` 中为每个事件提供强类型的 `ToPayload()/FromPayload()` 方法。如果 MVP-P0 确实想简化，至少应在文档中记录这个技术债务。

### 4.2 MemoryBus 同步模式的性能风险

方案 §6.4 默认 MemoryBus 为同步执行模式，并提到"handler 不能执行重 IO 或慢任务"。但方案 §12.1 StatsHandler 需要调用 repository 更新统计（涉及 DB 写入），这属于重 IO。

**建议**：
- 明确 StatsHandler 的统计更新在 MVP-P0 阶段使用"异步 goroutine + panic recovery"包装
- 或者在 MemoryBus 中提供 `PublishAsync` 变体，用 worker pool 控制并发度
- 至少在文档中标注此风险和缓解措施

### 4.3 `GroupMemberChangedPayload` 合并了过多语义

方案 §8.2 将 Ban/Remove/Mute/Recover 四个操作合并为一个 `GroupMemberChangedPayload` + `action` 字段区分：

```go
type GroupMemberChangedPayload struct {
    Action string `json:"action"`  // ban/remove/mute/recover
    ...
}
```

**问题**：
- 不同操作的必填字段不同（如 Mute 需要 `muted_until`，Ban 不需要）
- 消费者需要 switch action 来决定如何处理，增加了复杂度
- 与其他事件的粒度不一致（如 `GroupOrderPaid` 和 `GroupMemberActivated` 是分开的）

**建议**：保持合并方案可行，但必须在 `action` 字段使用常量（方案已提及），并且为每种 action 记录哪些字段是 required vs optional。

### 4.4 幂等规则缺少具体实现指导

方案 §11.4（LeaveGroup）、§15.3 提到了幂等规则："只有状态变化才发布事件"。但没有说明：

- **由谁判断状态变化？** 是 svc 层在发布前检查 `oldStatus != newStatus`？还是 repository 层返回 `rowsAffected`？
- **并发安全？** 两个请求同时 LeaveGroup，都读到 active 状态，都会发布事件？

**建议**：补充具体的幂等判断代码模式示例，或明确指出使用 repository 层的 CAS（Compare-And-Swap）更新来保证。

### 4.5 缺少事件版本管理机制

方案没有涉及事件 schema 版本化。当 payload 字段需要新增或变更时（如 `GroupJoinedPayload` 新增 `inviter_id` 字段），消费者如何兼容旧格式？

**建议**：MVP-P0 可以不加版本号，但在 DomainEvent 中预留 `Version string` 字段，初始值为 `"1.0"`。

## 五、测试缺口

### 5.1 缺少 MemoryBus 并发安全测试

方案中的 `MemoryBus.handlers` 是 `map[string][]Handler`，`Publish` 方法遍历执行。如果在 Publish 期间有 goroutine 调用 Subscribe，存在 data race。

**需要补充**：`TestMemoryBus_ConcurrentSubscribePublish` 竞态测试，或明确说明 MemoryBus 不保证并发安全（要求在 Subscribe 全部完成后再 Publish）。

### 5.2 缺少事件发布失败的业务连续性测试

方案 §10.3 说"事件发布失败不回滚业务"，但当前没有测试用例验证：
- Publisher 返回 error 时，svc 仍然返回成功响应
- Publisher panic 时，svc 能 recover 并返回成功响应（方案 §14 第 5 条要求）

### 5.3 缺少 Handler 错误传播行为测试

MemoryBus.Publish 在第一个 handler 返回 error 时就停止执行后续 handler。方案没有测试：
- Handler A 失败是否影响 Handler B 的执行？
- 是否需要"best effort"模式（继续执行剩余 handler，收集所有错误）？
